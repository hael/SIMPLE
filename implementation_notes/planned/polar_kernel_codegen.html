    Production polar kernels: faster code for the same per-pair sums¶

    Planned 2026-10-21 for an unattended night run on Hans's Mac (kit ~/agent_runs/runs/kernel_mac). It follows the measure-only benchmark of the same evening (polar_matching_layout_bench.md and its report, in the same directory of the worktree) and works in the same worktree, where the benchmark program is present but not committed.

    Why¶

    The benchmark scored synthetic polar spectra at the sizes of Cyril's two-state set (crop 160, 61 shells, pftsz 182, nrots 364). Two findings concern production code as it is, with no change of method:

    1. Production's per-pair sums are slower than the same source compiled elsewhere. The "replica" (production's euclid sums of gen_euclid_crvec, unshifted branch, and its inverse FFT, compiled in the benchmark module on a memo the benchmark rebuilds) ran 1.37-1.43 times faster at one thread, 1.33-1.41 at five and 1.22-1.26 at eleven. In the Debug build the two give the same bits; in Release they differ in the last bit in about 4 % of the 20-lowest lists, which the benchmark traced to how the compiler vectorizes the loop in each compilation unit. The suspected cause: the hot loop reads and writes arrays through components of the polarft_calc object (self%ft_ref, self%ft_ctf2, self%crvec1(ithr)%c, the last a pointer component shared with FFTW), so the compiler must assume they may overlap, and the accumulation mixes single and double precision per element (cmplx(acc + wk*c) with a double-precision wk).
    2. The distance conversion and the draw are a sixth of a pair. At one thread a pair costs about 10.8 µs in the sums, 0.6 µs in the inverse FFT and 2.3 µs in turning 364 values into distances (euclid_dist_from_crvec, one function call per rotation, in double precision, with a branch) and drawing among the 20 lowest.

    The dense table runs these kernels for every sampled particle against every reference. Since 2026-10-21 the multi-state stages 3-5 use the dense table again, so a faster per-pair kernel speeds up every such stage, and every single-state prob stage too, with no extra memory.

    Rulings that hold¶

    From the maintainer, 2026-10-21: the speed changes stay; NU filtering at stage 5 stays; no change of resolution policy. For this run: no change of method or layout (the matrix-product route waits for a measurement on the Dell); production code changes only in the polar calculator.

    Items¶

    1. Diagnose. Compile src/main/pftc/simple_polarft_corr.f90 and the benchmark module with gfortran's vectorization reports (-fopt-info-vec-optimized, -fopt-info-vec-missed, in a scratch build only) and, if needed, read the generated assembly of the two inner loops. Record which loops vectorize in which unit and why not. This decides the shape of item 2.
    2. The euclid sums. For gen_euclid_crvec (both branches) and gen_euclid_crvec_bank, move the accumulation over shells and angular bins into a private procedure of the submodule whose arguments are plain arrays (explicit shape or contiguous), with a local accumulator, called with the memo's sections. Keep the operation order and the precision of every element exactly as today (the same expression, the same conversions), so that the only difference can be the compiler's code generation. Then measure.
    3. The cc sums. gen_corrs and gen_corrs_bank (the cc objective, used where objfun=cc) have the same structure. Extend the benchmark with a cc case if that is quick (test side only); otherwise apply item 2's pattern, check identity and correctness, and report it as not timed.
    4. The distance conversion. In sample_euclid_crvec, gen_prob_euclid_val, gen_best_euclid_val and the bank path, compute the 364 distances in one loop that the compiler can vectorize (the same double-precision expression and the same treatment of overflow as euclid_dist_from_crvec, without a call per element). The result must be byte-identical. Leave the draw itself as it is unless an identical restructuring is obvious.

    How each item is judged¶

    • Speed. The benchmark's per_pair layout (production) against its value on the base build, on all six cases of the benchmark, at 1, 5 and 11 threads, best of three after a warm-up, nothing else running. The target for item 2 is the replica's speed.
    • Identity. The benchmark's check suite: the per-rotation distance vectors and the 20-lowest lists of production on the new build against the base build, at one thread, and each build at 11 threads repeated five times against its own one-thread run. Report the fraction of pairs that are byte-identical and the largest difference in units in the last place. Item 4 must be byte-identical.
    • Keep rule. A change of items 2 and 3 is kept when it is at least 5 % faster at 11 threads on the largest case and its distances differ from the base build by at most two units in the last place; otherwise it is restored and the report says why. Byte identity is preferred: if a variant reaches the replica's speed with byte identity, keep that one.
    • Correctness. The Debug build with the fast gate, the polar calculator's unit tests (simple_polarft_corr_tester and every unit suite that runs the polar calculator), and one high-level CTest entry that builds a probabilistic table (for example simulated_workflow_1jxy) passing its checks on the final build. Record whether that entry's outputs are byte-identical to the base build at one thread; a difference is not a failure if items 2-3 changed last bits, but it is reported.

    Phases 3 and 4: the x86 follow-up (Dell, run kernel_x86, 2026-10-22)¶

    Phases 0-2 ran on the Mac and were committed as ee5b68be1. On the Dell (Intel Core Ultra 9 285, hybrid: cpu0-7 performance cores with their own L2, cpu8-23 efficiency cores in clusters of four sharing an L2; gfortran 15.2, -O3 -march=native) the run ms_prob5check measured the new euclid kernel at 0.80-0.85x of the old one at 12 and 24 threads, 0.92x on one performance core and 0.81x on one efficiency core; cc 1.18x on a performance core, 0.92x on an efficiency core. Its reports showed the old euclid loops already vectorized there with 32-byte (AVX2) vectors and a run-time overlap check. Goal: understand why the new form is slower on x86 and find a form of the sums that is at least as fast as the old one on the Dell, likely to keep the Mac's gain, and equal to the old results to the last bit or two.

    Phase 3: diagnosis and candidates. Builds of the old form (f3ccb5fbd's simple_polarft_corr.f90 in an export of HEAD) and HEAD. Diagnosis of the euclid and cc inner loops in both forms: gfortran's vectorization reports and the generated assembly (vector width, shuffles for the complex interleaving, packing calls, the overlap check, unrolling), perf stat if available. Candidates, each a complete form of the euclid sums (both branches of gen_euclid_crvec, and gen_euclid_crvec_bank) and of the cc sums (gen_corrs, gen_corrs_bank), with every element's expression and precision kept: the old inline loops; HEAD's explicit-shape helpers; the old loops with a local pointer, contiguous alias of the accumulator (and of the memo slices if useful); helpers with assumed-shape contiguous dummies; helpers accumulating into a plain per-thread work array copied into the FFT buffer once per pair; any further form the diagnosis points to. Every candidate measured for euclid and cc on the two cases 1000x1 and 2500x4, pinned to cpu3 (performance) and cpu20 (efficiency), and at 12 and 24 threads, and its identity against the old form. Exit: the diagnosis, the table of candidates and the identity results in the journal and in Progress.

    Phase 4: the chosen form. The chosen form in simple_polarft_corr.f90, built and checked, and the report polar_kernel_codegen_x86_report.md (answer first; diagnosis; every candidate in every setting; identity; an appendix with the full source of every candidate's sums and call sites, so the Mac can measure the same forms; a commit message).

    Judging, fixed before any measurement. A candidate is acceptable when, on the Dell, it is not slower than the old form (f3ccb5fbd) by more than 2 % in any of the four settings (one performance core, one efficiency core, 12 threads, 24 threads) for euclid, and likewise for cc, and its distances differ from the old form's by at most two units in the last place. Among acceptable forms prefer the one that tells the compiler that the accumulator and the memo slices are contiguous and do not overlap (what the Mac needed). If no form is acceptable, the old form is restored for that objective. Production changes only in simple_polarft_corr.f90 and only to the form of the sums and their callers' argument passing; the distance conversion of ee5b68be1 stays. Speed is judged on the Dell only: it is closer to the machines SIMPLE normally runs on, and the Mac only has to build and pass its checks (maintainer, 2026-10-23).

    Progress¶

    Phases 3-4, 2026-10-23: the kernels on x86¶

    Phase 3: diagnosis and candidates (Dell, 2026-10-22/23)¶

    Done. Files changed: this plan (Phases 3-4, the file table, this section) and src/main/commanders/test/simple_commanders_test_highlevel_matchbench.f90 (the benchmark's middle team is now half the threads, so nthr=24 times 24, 12 and 1 on the Dell; nthr=11 still times 11, 5 and 1 on the Mac). No production file changed in this phase. Journal: ~/agent_runs/kernel_x86/state/journal_phase_3.md.

    Why the new form is slower on x86. gcc 15.2 applies unroll-and-jam (factor 2) to the shell loop of the new euclid_sums and to both shell loops of cc_sums. With plain array dummies it can prove that two shells may be interleaved; through the old pointer accumulator it could not. On the Mac this gave two shells per pass with de-interleaving loads and stores, a gain. On x86 with AVX2 gcc vectorizes the jammed loop with cross-lane permutes: the euclid loop takes 276 instructions per 8 bins x 2 shells (17 per bin and shell; the old loop 15), among them 36 vpermd, 16 vblendps, 18 reloads of permute constants and 24 register spills to the stack; the cc loop has 20 vpermd per iteration. The clean loop the compiler also emits (12.5 instructions per bin and shell) runs only for the odd last shell. Lane permutes are slow on the efficiency cores, hence 0.81x there against 0.92x on a performance core. Neither !$omp simd on the bin loop nor !GCC$ unroll 1 on the shell loop stops the jam (checked in the compiler reports; not timed). The old loop was already vectorized at full AVX2 width; it loads and stores the accumulator 8 bytes at a time, which costs less here than the permutes. A local pointer, contiguous alias does not change gfortran's code: the accumulator stays strided. The distance conversion of ee5b68be1 is not involved: it is byte-identical and alone makes the old sums 2.7 % faster on a performance core, 0.8 % on an efficiency core. Writing two shells per pass by hand avoids the jam and its permutes and is the fastest form on one thread, but it reads eight memory streams per pass (four arrays, two shells) and loses at 12 threads; forms that read at most four streams per pass (one euclid shell, or two cc shells) keep their gain in a team.

    How it was measured. Every candidate is HEAD's simple_polarft_corr.f90 with only the sums and their callers changed, built in one scratch tree (only that object recompiles), timed with the benchmark's production layouts per_pair (euclid) and per_pair_cc on the cases 1000x1 and 2500x4. P1 and E1: one thread pinned to cpu3 and cpu20, best of three after a warm-up, median of the pinned rounds (reproducible within 1 %). T12 and T24: the unpinned teams of nthr=24, as production runs them; these vary 10-30 % between launches (placement of the team on the two core types), so six rounds in rotating order (HEAD two, c14 four), median.
