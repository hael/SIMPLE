    2D tables, 3D tables and the NU filter, and 2D look and feel: the Mac run speed2d3d_mac¶

    Implementation note, 2026-10-19. Carried out 2026-10-19 (progress below; report in speed2d3d_run_report.md). The execution plan of the unattended ten-hour run speed2d3d_mac on the maintainer's Mac. The design is in speed_architecture_proposals.md (sections 1.2 b and d, and 1.3) under doc/implementation_notes/planned/; what the previous Mac run did is in doc/implementation_notes/completed/speed2D_run_report.md. This note holds the run's items, tests, phases and progress. Where this note and the proposals note disagree, this note holds: it was checked against the code at af13bc828 on 2026-10-19 (section "What the reading found").

    Rulings of 2026-10-19¶

    • The chunk: finish the 2D work (the 2D tables and the master's work between them, then the 2D look and feel), and the 3D table, shift-search kernel and NU filter items. Every item of Phases 1 to 3 leaves results byte-identical at one thread.
    • Last, only if time is left (Phase 4): the 2D table prepares its particles from the same in-memory cropped image the 2D search has used since af13bc828, and the shared-memory particle buffer keeps those cropped images. This changes uncached results by rounding (accepted with the package); its identity is judged against cache=yes runs of the base build, which must come out byte-identical.
    • Testing as in the previous run: one-thread identity on the simulated cases, and for every new or changed parallel region a thread stress test at the Mac's full thread count, repeated; one multi-threaded run per phase to catch crashes and races.
    • Not in this run: the master drawing the stage 1-2 sample, partition balancing by active particles, the maxits/minits, fillin and prob_snhc renames, the particle-cache and nsample defaults, "one project owner on the master", the correlation's shift-independent term (it is not identical, below), and any edit of stream code (src/main/stream, commanders/stream: Joe's area; list what would change there in the report).

    What the reading found¶

    Checked on 2026-10-19 at af13bc828; the run trusts these only after re-reading the code.

    • The master's 2D pre-step time is the sparse table. On msp1 (141,838 particles, 150 classes, 10 parts) the 3.8-4.3 s of ref_assign and the 1.6-1.8 s read per iteration fall in the prob_snhc iterations (solve2D stages 3 to 5), which use the sparse 2D table; the dense stage 6 assigns in 1.09 s. The parts score 131-148 of 150 classes per particle, so the sparse table is nearly full (~/Processing/msp1/BENCH/PROB_ALIGN2D_BENCH.txt, read-only).
    • The 2D tables. The master holds loc_tab(nclasses,nptcls) of prob_candidate (six 4-byte fields, 24 bytes; 511 MB on msp1), filled in parallel inside the timed read. A part file is a header, the particle indices, the seed table, then chunks of particle indices and 24-byte candidates (28 bytes per entry). The dense reader (read_tab_to_glob) runs part by part, serially, with no file-size check, no format word and no check that a particle is in exactly one part. The sparse reader (read_tabs_to_glob then read_sparse_tab_to_glob) reads every part twice: once to count candidates per particle, once to read them. Reading arrays of a derived type may move one component at a time; time it before relying on it.
    • The sparse 2D assignment (ref_assign_sparse_likelihood): building the class lists is serial (a count pass and a fill pass over all candidates, then per class a gather of distances and an hpsort of about 140,000 values); the frontier loop then runs once per particle (sample_likelihood_index sorts about 150 values and draws one ran3()), scans the particle's candidates three times (search_frac, search_npeaks, update_frontier_after_assignment) and walks class heads with random reads. The only random draw is one ran3() per loop iteration, in assignment order. hpsort is not stable: its order among equal distances decides a class's head, so it stays. The swap-remove in sync_frontier_class decides ties within a particle, so the order of classes within a particle stays.
    • The 3D master table is already particle-major. rows(nrefs,nptcls) keeps each particle's references contiguous. The assignment's main loop sorts each reference over all particles and reads rows(iref,i)%dist with a stride of nrefs*8 bytes; that is the loop that does not stream. The useful change is the opposite layout (each reference's distances contiguous). read_dense_part issues one read per particle, though a part's rows are one contiguous block in local order.
    • The correlation's shift-independent term is not identical when hoisted. The reference norm in the correlation kernels is computed from pft_ref*shmat_8*ctf; the shift matrix's modulus drifts by rounding along its recurrence and the term depends on irot, which changes during an alternating search. Computing it once per minimisation changes results. Only fusing the shift matrix into the kernel loops can be identical.
    • The NU filter's label optimisation (optimize_nu_cutoff_finds) runs 35 tent smoothings at 8 candidates plus up to 7 re-smoothings of the mask norm; the level-1 values equal the setup's smoothed candidates bit for bit, so reuse cuts 42 smoothings to 28. Skipping all-zero lines and blocking the strided passes of the tent smoothing, and packed voxel lists per colour in the Potts sweeps, keep every operation; replacing the neighbour sum by label-histogram counts would not. estimate_nu_label_smooth_beta uses an OpenMP real reduction, so the filter is identical only at a fixed thread count (as today).
    • 2D look and feel. check_conv2D prints CONVERGED: .YES./.NO. before its callers apply minits, maxits and full-assignment coverage, so the printed verdict can contradict whether the run stops; it prints a PROB NEIGH MODE line that means nothing in 2D and the SDEV/MIN/MAX of a low-pass that is the same for every particle. The solve2D stage line's format (A,I3,A9,F5.1) cuts ' WITH LP =' to >>> STAGE 3 WITH LP 12.5. No line marks entering and returning from a refine2D stage. prob_align2D and the 2D assignment print 7 to 10 lines per iteration. The stage table's MAXCLSPOP column prints the dead max_cls_pop (always 0). On the distributed master params%lp is never updated (the workers set the band), so a 3D-style "this iteration" low-pass line must print the particles' lp field. check_conv2D also writes the stats file's keys (an output: unchanged) and is called by the stream pool (its log lines change there too; nothing parses them).
    • The solve2D interface shows defaults that the code does not apply: center shows no (the code uses yes), lpstart 30, lpstop 6 and cenlp 30 (the code derives them from the mask diameter). The displayed numeric defaults come from scripts/default_audit.py at build time, which does not follow exec_solve2D into exec_solve2D_workflow, so no solve2D block is generated. nsample is Advanced in solve2D (Standard in solve3D) and shows 0 (the 2D default is 200,000). nstages is read but not exposed; in 2D it re-spaces the low-pass ladder (in 3D it truncates the plan), so the wording differs. refine=snhc_smpl is listed without explanation: it differs from the default only in the last stage. type(ui_program) :: refine2D in simple_ui_refine2D.f90 is never constructed (dead).
    • Class-average file names are built inline in about fifteen places (the solve2D commander and controller, the refine2D strategy, the 2D matcher, make_cavgs, the star-file writer, nano2D; stream has five more), some with params%ext and some with MRC_EXT; make_cavgs reads the iteration back out of a name by offset. simple_refine3D_fnames.f90 is the precedent; its refine3D_iter_refs_fname is called nowhere.
    • Sigma2 helpers. prepare_canonical_sigma_update is identical in the 2D and 3D strategies; record_sigma2_bench_context differs only in the bench type; ensure_canonical_sigma2 differs (objective check, iteration, label, a reuse line). Further variants live in the make_cavgs, rec3D and solve2D code.

    Why thread stress testing¶

    The run speed_mac's parallel read of the dense table parts passed one-thread identity, yet held a race the maintainer fixed in commit 43de9b340: string temporaries built inside the OpenMP loop and handed to fopen, a coverage check that needed atomic capture, and a work array sized by nthr_glob while its loop ran on omp_get_max_threads() threads. One thread runs an OpenMP loop serially, so identity can never show thread safety. Rules for every parallel region this run adds or changes:

    • No string or allocatable-character temporaries, and no calls into routines with module-level buffers, inside the region: build file names and messages before it.
    • Work arrays sized by the team the region actually uses.
    • Errors inside the region set a status per task, raised after the region.
    • A tester check that runs the routine at one thread and at the Mac's full thread count (omp_get_num_procs()), at least 20 times, and compares bit for bit where the result is deterministic by construction; where it is not (dynamic schedules that move random draws), every run must complete with finite results.

    The clock¶

    The run has ten hours from its launch: launch.sh writes the launch time and the deadline into the run's state/ directory and each phase prompt states them. The report and full.diff (Phase 5) are written before the deadline.

    • Check the clock before starting each item. Do not start an item that cannot be finished, tested and snapshotted, and still leave the phase-end runs (about 25 minutes) and the 45-minute close before the deadline; write it up as not done, for time. In Phase 3 leave another hour for AD1 and CR1.
    • AD1 and CR1 run at the end of Phase 3. If Phase 3 is cut or skipped, they run in the background at the start of Phase 5 and the report states their verdict (or that they did not finish).
    • Phase 4 starts only if at least two and a half hours remain. The phase loop also skips a phase that would start less than 45 minutes before the deadline, so that Phase 5 always runs.
    • Inside a phase the items are in priority order: when time runs short, the later ones go.

    The items¶

    Phase 1: the 2D tables and the master's work between them¶

    1. Timers first (benchmark output only). Split the PROB_ALIGN2D report's read and assignment lines: the sparse read's two passes; the assignment's class-list building (counting, fill, per-class gather and sort), frontier loop and leftover particles, for both the sparse and the dense assignment. Run E2 and R2 on the timer build and record where the time goes on these small cases, as an indication only.
    2. One pass over each sparse part file. The 2D part file carries the candidate count of every particle after the particle indices, as the 3D neighbourhood table does; the master sizes its ragged store from the counts and reads every part once. Read into intrinsic arrays (indices, distances, in-plane indices, shifts) and then build the store, if the timer shows the derived-type transfer is the cost.
    3. Parallel 2D part reads for the sparse and the dense table, as 3D's read_dense_part does: an OpenMP loop over the parts with a status per part raised after the loop, a file-size check against the header, a format word, and a check that every particle is in exactly one part (with atomic capture). File names built before the loop. Stress test.
    4. The sparse 2D assignment's class lists in parallel. The per-class gather and hpsort run in parallel over classes with work arrays sized by the team; gather the distances class by class during the fill pass; keep each class's particle indices in their own contiguous array so the head walk reads sequentially; compute each particle's npeaks once. The frontier loop keeps its order and its single ran3() draw per iteration, the swap-remove order of sync_frontier_class and the unstable hpsort. A tester keeps the present routine as the reference and compares the assignments on synthetic sparse tables, ties included, at 1 and 11 threads.
    5. The compact dense 2D record. As 3D: 8 bytes per entry (distance and in-plane index; the class is the row index), plus a list of refined entries (particle, class, shift) for the entries whose shift was refined (at most nhood_sz per particle); membership in the list stands for has_sh. A format word and a class-count check in the header. The master holds the rows and the refined list in compressed-row form and rebuilds a full candidate through an accessor; the old 2D dense reader goes (part files live for one iteration; no older format is read). The 2D tester writes the old format and sets loc_tab directly: change it with the format. Teach the lossless part-file decoder the new layout and compare every field both layouts hold, bit for bit.
    6. The frontier loop's sort (only if item 1 shows the loop dominates after items 2-4): a top-k selection instead of sorting about 150 values in sample_likelihood_index, falling back to hpsort whenever equal values reach the top k+1. A tester compares it with the present sampler on random and tied inputs, draw for draw.

    Phase 2: 2D look and feel (outputs unchanged; log text and interface text change)¶

    1. Log lines as in 3D. One >>> CONVERGED: yes|no per iteration with the final decision, after minits, maxits and coverage (the decision logic unchanged); >>> % PARTICLES USED FOR UPDATING THE MODEL; >>> MATCHING LOW-PASS LIMIT (THIS ITERATION) from the particles' lp field; the meaningless PROB NEIGH MODE line and the spread of a constant low-pass gone; the stage line >>> STAGE n WITH LP x A (format fixed) and the gold-standard stage line in the same style; >>> SOLVE2D ENTERING REFINE2D STAGE n and >>> SOLVE2D RETURNED FROM REFINE2D STAGE n with a flush; prob_align2D and the 2D assignment one line per iteration; the stage table without the MAXCLSPOP column, and the dead max_cls_pop deleted. The stats file's keys stay. check_conv2D has two callers, the 2D matcher (shared memory, and the stream's 2D pool through it) and the refine2D strategy (distributed); each prints the final verdict after its own minits/maxits/coverage decision, so the stream pool keeps one convergence line per iteration without any edit to stream code.
    2. The solve2D interface.     • Timers. The PROB_ALIGN2D report has a section that splits the reads (the parts' heads, their candidates) and the assignment (class lists: counts, fill, sort; the frontier loop; the leftover particles).
    • One pass over each sparse part. The 2D part file of the candidate stream has a format word (-4) and the candidate count of every particle after the particle indices. The master reads every part's head, sizes its store from the counts, and reads every candidate once.
    • The compact dense record. The dense part file (format -5) holds one row of (distance, in-plane index) per particle and class, 8 bytes per entry, then the refined entries (particle, class, shift). The master keeps the rows and the refined entries in compressed-row form and rebuilds a full candidate when it assigns. R2's part file shrinks from 432 to 155 kB.
    • Parallel reads. Both passes run in parallel over the parts. Each part's size is checked against its header, and a particle in no part or in several stops the run. Errors are raised after the loop.
    • The sparse assignment's class lists. Each class's candidates, with their particles and distances, are gathered during the fill, sorted in parallel over the classes with the same unstable hpsort, and walked sequentially. Peak counts are computed once. The frontier loop, its one draw per iteration and its tie order are unchanged.
    • Tests. The 2D tester writes its part files through the table's own writer, checks that a refined shift survives the dense layout, reads 7 parts at one thread and 20 times at every processor (both layouts), and compares the sparse assignment with the algorithm it replaced on tables with ties, at four draw seeds and at one thread against every processor.
    • Not done. The top-k sampler of the frontier loop: on E2 every phase of the read and assignment takes 1 to 3 ms of a 2 s iteration, so the frontier loop does not dominate. The timers settle it on a large case.
