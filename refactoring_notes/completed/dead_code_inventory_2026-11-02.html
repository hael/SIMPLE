    Unreferenced code inventory¶

    Status: completed review; archived on 2026-11-04. The two approved changes, native EPU XML reading and loading the test molecules from PDB files, were delivered in ef5fe84d5. The other deletion proposals were withdrawn by the owner's ruling below. This record authorizes no further code removal. Its measurements and reachability claims describe the dated audit, not a new validation or deletion list.

    Historical inventory, 2026-11-02, against master at 703a7e825. Identification only: nothing was deleted by the audit. The question was which code we compile and test over and over although nothing uses it. Appendices A-C list what the analysis found; appendix D says how to rerun it.

    Owner ruling 2026-11-02: the lists of sections 3, 4 and 6 and appendices A-C are not deletion lists. They contain mission-critical code. That no procedure in master calls a routine does not make it dead, and this inventory was wrong to call it that and to propose deleting it. Nothing on these lists is to be removed on the strength of this analysis. What stands: section 1 (the XML library, replaced) and section 2 (the molecule data, moved to PDB files read at run time).

    The finding that matters most: dead code is a small part of the compile time. Of the 1 001 s a clean build spends compiling (sum over 935 jobs), SIMPLE's production code takes 69%, the test code 28% and all vendored libraries together 3%. SIMPLE's own dead code is about 2%, and the slowest files are slow because of what they import, not because of their size (simple_commanders_ori.f90 compiles for 11.9 s; its two dead commanders are a quarter of its lines). Removing everything in this inventory makes the tree smaller and the reviews and tests easier; it does not make the build much faster. The levers on build time are the test code (--exclude-tests already drops it from a developer build) and the umbrella imports of the commanders, which doc/policies/compile_time_policy.md already targets.

    What I would do, in order of payoff:

    1. Replace the XML library (67 files, 53 600 lines, 1.7% of the compile time) by one routine of about 40 lines: SIMPLE uses it only to read two numbers from EPU metadata (section 1). Done 2026-11-02.
    2. ~~Delete the code nothing reaches~~ Withdrawn: see the ruling above.
    3. ~~Rule on the owner decisions below~~ Withdrawn with it, except decision 2.

    Decisions for you:

    1. The GPU and OpenMP-offload code paths are unreachable (simple_reconstructor_openmpoffload.f90, the cuFFT/GPU distance routines of simple_polarft_corr.f90, about 600 lines). Retire them, or are they the start of a GPU port you want to keep?
    2. The 56 500-line simple_molecule_data.f90 (the atoms of 1JYX and 6VXX) is test data compiled into the core library. Move it to PDB files the tests read, or leave it? Ruled 2026-11-02: move it to PDB files in the repository, read when needed.
    3. Production code that only the tests reach (section 4, appendix B): retire the features among it with their tests (Canny edge detection, the batch polar projector, ...)? The test oracles and helpers stay.
    4. 65 registered programs have no test, no internal caller and no NICE reference (appendix C). They are live code, so only you can say which are obsolete.

    Method¶

    A reachability analysis of every Fortran source the build compiles (src/, production/, the two generated sources simple_args.f90 and simple_ui_default_values.f90, the #included macro files):

    • Nodes: every procedure, derived type, generic interface and module variable.
    • Roots: the production programs (simple_exec, single_exec, simple_stream, simple_private_exec, simple_persistent_worker), separately simple_test_exec, and every bind(c) procedure (444).
    • Edges: an identifier in a reached node reaches every node of that name in a module visible from it (the node's own module and, transitively, what it and its procedure use, so re-exports count); %name reaches the bindings of that name of every reached type, generic bindings their specifics; generic interfaces their specifics; a reached type its final procedures and defined operators and assignments, a reached module its operator and assignment interfaces; use-renames are followed. Both branches of every #ifdef count, so code only a GPU or Windows build uses is not called dead.
    • Classes: live (reached from a production program), test-only (reached only from simple_test_exec), unreachable (reached from neither).

    The analysis can only err towards calling dead code live (a dead procedure sharing a name with a visible live one is kept), not the reverse, except through a parsing error. Three checks against that:

    • The linker. A build with -ffunction-sections -Wl,--gc-sections, then the symbol tables of all six executables. Of the 442 unreachable SIMPLE procedures, 178 are in no executable. 255 are type-bound procedures of live types: a type's vtable references every binding, so the linker cannot drop an uncalled method; the analysis found no %name call of them in reachable code. The remaining 9 the linker keeps are called only from those uncalled methods (checked one by one). No procedure the analysis calls unreachable is kept by the linker for any other reason.
    • Spot checks of the largest candidates by hand (rg of every name): no caller outside dead code, or only mentions in strings, logs and umbrella import lists.
    • No implicit calls: SIMPLE has no defined derived-type I/O and no declare reduction; C code calls Fortran only through bind(c); procedure pointers are assigned by name, which the analysis follows.

    What it does not see: programs a user starts by hand are live by definition (section 6 lists the ones nothing else touches), and a binding called only through a name the analysis cannot resolve would be missed. Neither weakens the "unreachable" verdicts above.

    1. The XML library¶

    Done 2026-11-02. src/fileio/simple_epu_xml.f90 (read_epu_beamshift, with the unit_core sub-suite EPU XML) replaces the library at the three call sites, which now log a file without a BeamShift and go on (the DOM lookup crashed on one); src/extlibs/xml and its CMake glob are gone.

    src/extlibs/xml (FoX: 67 files, 53 600 lines, 17 s) has three users, and all three do the same thing: parse an EPU metadata file and read BeamShift/a:_x and BeamShift/a:_y (simple_relion.f90:588, simple_starproject.f90:918, simple_preprocess_strategy.f90:305, the same seven lines each). 25 000 of the library's lines are unreachable even so, 24 of its files entirely.

    Proposal: one routine in src/fileio that reads the file, finds <BeamShift> and returns the two numbers between <a:_x>/</a:_x> and <a:_y>/</a:_y>, called from the three places; then delete src/extlibs/xml and its CMake glob. Needs one or two real EPU XML files as a unit-test fixture.

    Appendix D: rerunning the analysis¶

    The tools are outside the repository, in /data2/agent_runs/dead_code_2026-11-02/tools/ on the build box (deadcode.py, about 500 lines of Python 3.12, read-only). deadcode.py <generated sources> writes every node with its class as JSON (77 s for the whole tree); why.py <name> [P|T] prints the chain of references by which the analysis reaches a node; summarise.py and files.py tabulate. The generated sources are lib/simple/simple_args.f90 and lib/simple/simple_ui_default_values.f90 of any build tree. The linker check is a Release build with -ffunction-sections -fdata-sections and -Wl,--gc-sections, then nm --defined-only of the six executables. If the analysis is worth keeping, it can move to scripts/ with a short usage note.
