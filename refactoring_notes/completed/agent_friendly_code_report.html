    Agent-friendly code: report of the run agent_friendly¶

    2026-11-05, on the dell, unattended. Plan: agent_friendly_code.md (sections 3, 5 and 7 say what and why, section 8 how the run was scoped and judged). Its Progress section holds the detail of each phase, with every number and log path. Base: 6565f5ba5. Logs: /data2/agent_runs/agent_friendly/scratch/ (scratch/ below; ~/agent_runs/agent_friendly links to the run directory).

    What was learned¶

    • Checks find defects that guides only describe. Turning the silent rules of 3.1 into stops found real defects along the way:
    • rot_to_asym returned an uninitialised record under c1 at the south pole;
    • eo=-1 particles were summed into the even half;
    • the gridding density files had no header, so a reader of the wrong box read a prefix without a word;
    • read_segment(..., fromto) ignored the range for .simple files, and its string branch stored rows at the wrong index;
    • export_cls2D changed the project it exported;
    • icosahedral maps aligned by the symmetry search were in another setting than refinement uses (phase 4, O1).

    Each new check is a tester assertion that fails on the code before it: 134 assertions in 13 suites on the base for phase 2's fixes, and 8 on the previous phase's code for phase 3's. - A static check of the command-line chain was cheap and broad. scripts/check_cli_chain.py, now in the fast gate, reported 196 problems on the base: 93 keys accepted and silently ignored, 94 yes/no keys taking any value, 4 user-interface inputs that stopped the program, and 4 private programs never checked. It passes now. - Behaviour-preserving work can be proven byte for byte; behaviour-changing work needs attribution. The phase-3 renames and moves left every workflow output identical. One ruled fix of phase 2 (X5, the atomic centre at ldim/2) changes the simulated input of every workflow entry, so the entries' numbers moved. Rebuilding the tree without that one fix showed that nothing else changed apart from two ruled project keys. - One run of a de novo workflow cannot judge quality. simulated_workflow_6vxx does not depend on SIMPLE_SEED, and one data set shows only "different". The 3.7 judging runs (deferred) are what would show better or worse. - Premises need measuring. O4's ruling assumed every L-BFGS-B client passes its tolerance into the line search. The shift search does not. Handing it the textbook line-search constants made it worse (271 instead of 150 evaluations, larger shift errors). - A Fortran language server copes with SIMPLE. fortls 3.2.2 indexes all 832 files in 1.6 s at 216 MB. It resolves use chains and type-bound bindings, reaches submodule bodies in two steps, and gives exact references for type-specific bindings. Generic calls resolve to the binding only, and the JSON library gives false errors.

    What changed, phase by phase¶

    The driver's /home/elmlundho/agent_runs/agent_friendly/review/phase_N.diff files for phases 0 to 5 hold only the changes to .github/skills and the generated Fortran indexes: no Fortran source, no plan, no new file (phase_4.diff is empty). The complete per-phase diffs for those phases were rebuilt from the driver's phase-start snapshots and HEAD by scratch/keep/full_diffs/make_full_diffs.py: scratch/keep/full_diffs/phase_N.diff, with a file list and line counts in phase_N.stat. The engine was fixed before phase 6, so review/phase_6.diff and review/full.diff are complete. The whole change is git diff 6565f5ba5 of the working tree plus its untracked files.

    Phase 6¶

    The maintainer accepted every recommendation of the report ("I accept everything. Let's finish this up.") and ruled that nothing in bounds stays deferred. The sieve came into bounds; the items that need ms_posterior2's files go to the follow-up run agent_friendly2. The ruling is recorded in the plan's sections 8.1 and 8.3.

    What was learned: - The new stops caught nothing in the existing workflows, and the two the code itself needed were already ruled: O1 for icosahedral runs, and the slot producers. - Without O4, the phase's tree reproduces phase 3's workflow outputs exactly. - The Debug build, where the slot stop is active, runs every unit suite and the library label without tripping it. - So the X1 and G3 completions, the slot stripping, the atomic rename, the CTF memo check and the sieve fix change no result, only what happens when a rule is broken. - The icosahedral axis search is not exact. After O1 its aligned map scores 0.91 to 0.98 under the builder's operators, against 0.495 in the old setting, and the value changes between runs. The O1 test therefore asks for the suite's control ceiling, not its exact-target floor. - One stop caught a tester's own design. The first version of the stale-slot test passed on the old code, because evaluating an invalid slot already stopped there. Checking each new test on the previous tree found it.

    Evidence: fast gate 15/15 in Release and Debug; test=units 152 groups, 14,910 assertions, all passed in both; the library label 7/7 in Release (in Debug, with the slot stop active, it tripped nowhere). The new checks fail on the phase-5 tree: 13 assertions over 6 suites. The workflow entries differ from phase 3 only through O4: whole-volume correlation 1jxy 0.645, 6vxx 0.509; the defocus errors move by 0.1 nm or less. Details and log paths: the plan's Phase 6 Progress entry.

    Decisions taken under delegation¶

    Each is recorded in the plan's Progress entry of its phase.

    • Phase 1: 86 declared fields that parameters derives are marked "not a command-line key" and left out of the accepted keys, rather than bound. Seven accepted-but-unbound keys that programs or the user interface name are bound. No parameter was added.
    • Phase 2: C5 is narrowed to "a partition worker (not stream=yes) may not write its input project". Stream jobs own their job projects.
    • Phase 2: stops that can fire inside OpenMP parallel regions (the polar calculator's memo and weights checks, polarize*, apply_ctf) are kept as fatal stops for programming errors, with fixed messages.
    • Phase 2, from the diff review: I5 was extended to the polar calculator and the class sums; esig%kill bumps the spectra counter; score_project_cavgs also restores the worker identity.
    • Phase 2: test children that write a project first set one OpenMP thread, so a regression fails the suite instead of hanging it.
    • Phase 3:
    • N10 takes the investigator's design A: the service applies the request's settings and restores the caller's. Design B (consumers read the request) would need the out-of-bounds refine3D strategy.
    • The renames stay within the five folders the file table allows.
    • V2's trailing-chain manifest version was raised, so old chains are re-seeded.
    • Phase 4:
    • I1 judged by solve2D over nine seeds plus the workflow entries;
    • O1 judged by a symmetrized two-blob map and a c1 against pgrp=i reconstruction;
    • O4 judged in three variants for the CTF fit;
    • S4 on synthetic beam-shift patterns, because no data on the machine has per-micrograph beam shifts.
    • Phase 6:
    • O1 deletes RELION's icosahedral table and the icorelion argument, which the change made unused.
    • O4 states the shift search's strict line search at its calls.
    • The slot stop is compiled in Debug builds only (_DEBUG).
    • The slot producers follow the ruling: frame is read back after a write, so it became a slot. The CTF and optics constants are not read back, so they are stripped where they are copied in.
    • G3 changes allocation sizes only, not the parallel regions' code; roavg keeps its own forced team.
    • simple_rename keeps an ignored overwrite argument for one out-of-bounds caller.
    • The O1 test asks for the control ceiling, after four phantom geometries.
