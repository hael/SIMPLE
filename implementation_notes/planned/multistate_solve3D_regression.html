    Multi-state solve3D regression: diagnosis on a simulated two-state set¶

    Planned 2026-10-21 for a Dell run of about two days (arun run ms_regression), base 72930a3a4. Revised the same day after the maintainer's rulings (section "Rulings"). Nothing in this note has been run yet. The facts in "What we know" were read from the code and the history and checked by a second reader; the run checks again whatever it relies on.

    What was reported¶

    Cyril (2026-10-20): two runs of de novo solve3D with nstates=4 on his real data ("Sov") no longer give what he obtained before, which was four states with a fair bit of smearing. He also has a simulated set of 30 000 particles in two states that he cannot reproduce. The set is in ~/Processing/simulated_vcrnapol with the script that makes it (generate.sh). He does not know which build gave his earlier result.

    Two failed runs are not yet proof of a regression: on our own three-state test the de novo route resolves every state in only 13 of 20 runs. The run therefore compares how often builds separate the states, and where in the stage ladder the separation forms or is lost.

    Terms¶

    • State: one of the nstates structures a multi-state refinement reconstructs. Each particle carries a state label; state 0 means the particle is excluded.
    • Stage: solve3D runs a ladder of refine3D executions ("stages") at increasing resolution. With nstates>1 there are five: stages 1-2 use shc (stochastic hill climbing, in which states and projection directions are searched on an equal footing), stages 3-4 use prob (assignment from a table of particle-reference scores: projection directions drawn at random, the state taken as the best over all states), stage 5 uses prob_neigh in state mode (the same over a neighbourhood of directions shared by the states). Each stage has a planned low-pass limit (its "rung") and a maximum number of iterations.
    • Distributed / shared memory: nparts>1 runs a master process plus worker processes per iteration; without nparts one process does everything. Cyril runs distributed (nparts=3).
    • res05: the resolution at which a state's half-map FSC falls to 0.5.
    • Resolution-limit updates: the rules that move a stage's limits during a run: stage omission (a stage is skipped when res05 is already finer than its rung), FSC=0.5 promotion of a stage's limit, the mid-stage exit (a prob stage ends once res05 passes the next rung), and the matching limit taken from the NU hand-off.
    • NU filtering and NU hand-off: nonuniform low-pass filtering of the reconstructed maps during assembly, on from stage 5; the hand-off is the limit the filter reports back for matching. The matching limit never goes finer than lpstop, 6 Å for multi-state.
    • Accuracy: the fraction of the particles active at the start of solve3D whose final state equals the true state, taking the better of the two ways to match found states to true states; state 0 counts as wrong. Putting every particle in one state scores 0.567 on this set.
    • ARI: adjusted Rand index between found and true labels (0 for random, 1 for perfect).
    • Signature: the stage at which accuracy rises above 0.75 or falls back, plus the stages omitted or cut short, read from the labels written after every stage and iteration.
    • Anchor: an older build expected to work, measured beside the current one.

    Rulings¶

    Of 2026-10-21, on the first version of this note:

    1. The speed changes stay. Nothing obtained in the speed refactoring is given up: the multi-state schedule (prob_neigh in stage 5, the stage-2 scan exit, the 2 500-direction cap), the table and assembly changes. A diagnostic variant may undo one of them to localise a cause; a fix may not. A per-run time of at most 30 minutes is expected.
    2. NU filtering at stage 5 stays as it is, whatever the evidence; it is not varied.
    3. Resolution-limit updates may change for nstates>1 and stay exactly as they are for nstates==1.
    4. Distributed and shared memory are equivalent. Where they differ, the difference is a defect and is fixed.
    5. Stages 1-2 stay as they are: shc with sticky sampling treats states and projection directions on an equal footing, which is the approach that worked in the past.
    6. A temperature on the state assignment in stages 3-4 is welcome. Going straight to the greedy state assignment in the probabilistic step may be unwise. From stage 5 onwards the assignment stays as it is now: projection directions drawn at random, states greedy.
    7. An emptied state is re-seeded by a balanced random relabelling; a restart of the ladder may have to be considered when that happens.

    Earlier rulings that hold: de novo multi-state stays, without several starts and selection (2026-10-18); sampling and relabelling are never driven by the maps or poses (2026-10-04), so no fix relabels particles against the current maps; state 0 means exclusion and a true state in state 0 is a failure (2026-10-17); de novo routes are judged over many runs, never one (2026-10-18); bugs found are fixed in the run (2026-10-17).

    Readings of these rulings that the run follows (correct them before launch if they are wrong):

    • Ruling 1: a time change that comes only from a multi-state resolution-limit rule (more iterations because a stage is no longer omitted) is allowed by ruling 3 and is reported per stage; a slower kernel, table or assembly is not allowed.
    • Ruling 4 covers the frozen stage-1 references and the empty-state handling (long-standing items 1 and 2): both are fixed, single-state included, since shared memory already does the right thing.
    • Ruling 6: the temperature is a parameter (default greedy, so refine3D outside solve3D is unchanged) that solve3D sets for stages 3 and 4 only. A particle's state is drawn from a softmax over states of its best score in each state, divided by the temperature; projection directions are then drawn within the drawn state as now. The run implements it in its own phase, chooses the values by a small sweep and keeps it only if it does not lower the separation counts.
    • Ruling 7: whenever a state is empty (or below the prob stages' minimum population) at a stage start, all active particles are relabelled at random with balanced populations, in both modes and for any number of states (today an empty state 1 stops a prob stage, three or more states with an empty last state stop, and shared memory relabels only at the first iteration). The run counts these events and whether runs recover from them; a restart rule is proposed from that evidence, not implemented.

    What we know before any run¶

    The simulated set¶

    generate.sh simulates 17 000 particles of EMD-51275 (labelled state 1) and 13 000 of EMD-51273 (state 2), box 180 at 2.055 Å, SNR 0.1, CTF with 2 ± 1 µm defocus, random poses, shifts up to 3 pixels, B-factor 100 ± 5. It stacks and shuffles them, imports them with deftab=, runs solve2D ncls=10, then solve3D single-state and with nstates=2, each with nparts=3 nthr=16.

    Checks made on 2026-10-21:

    • The two maps are not in a common frame (real-space correlation 0.12 as given). After a rotation search they agree closely: FSC 0.94 at 120 Å, 0.83 at 30-50 Å, 0.48 at 13 Å, against 0.99 for identical maps at the lowest shell. About 30 % of the density differs. This is a moderate difference, visible at low resolution, so 30 000 particles at SNR 0.1 should separate reliably with good poses. Found maps are compared with the truth after docking, in both hands. Corrected in Phase 0 (see Progress): docked with dock_volpair, the two maps agree more closely than this, FSC 0.88-0.90 at 30-50 Å, 0.81 at 13 Å and about 0.75 from 7 Å to 4 Å, so the states differ less than assumed here.
    • import_particles deftab= takes only CTF parameters, state and eo from the file, so neither poses nor labels leak into the project (the script sets every state to 1 first). The import stores the stack by absolute path, and project row i is stack image i.
    • stackops nran=30000 draws a permutation without repeats and carries each particle's parameters with it, so out.txt line i describes stack image i.
    • labels.txt is column 17 of out.txt. Which column holds state= depends on how SIMPLE writes the parameter line, so the run takes the labels by key and compares them with column 17.
    • The set must be generated without SIMPLE_SEED, as the script does. Every SIMPLE process restarts the seed sequence, so with a fixed seed the two make_oris and the two simulate_particles calls would draw the same poses, shifts and noise for the first 13 000 particles of each state.

    Candidate causes, and what tells them apart¶

    1. Frozen stage-1 references in distributed runs (long-standing item 1). Old, but it matters more now that stage 2 is shorter: in a distributed run the states can only start to form in stage 2. Signature: shared memory separates where distributed does not; accuracy after stage 2 low in distributed runs.
    2. Stage 2 shortened (10-16, a speed item that stays). Signature: fewer stage-2 iterations and lower accuracy after stage 2 than the anchor.
    3. Resolution-limit updates cutting stages 3-4 (10-18, 10-19). At the start both states hold mixtures of nearly the same structure, so the best state can reach FSC=0.5 early and the prob stages, where the states split, can be skipped or shortened. Signature: the log lines SOLVE3D OMITTING STAGE, STAGE RESOLUTION EXIT and promoted by FSC=0.5; no states_stage3.txt or states_stage4.txt (an omitted stage writes none); short stages.
    4. Greedy state assignment in stages 3-4 with the prob table of 10-15. The state is the argmin over all references, and only the best references across all states get a refined shift, so the leading state is favoured; a state that falls behind early cannot come back. Signature: stages 3-4 run their full length but gain less accuracy than in the anchor, or one state's population drains during them.
    5. Stage 5 (prob_neigh in state mode since 10-16; NU filtering since 10-18, which stays) and the matching limit taken from the finest NU hand-off over the populated states (a resolution-limit update). Signature: separated after stage 4, lost in stage 5.
    6. A defect in the speed and structure changes, for example a thread race or a state indexed wrongly, which one-thread identity cannot show. Signature: a crash, NaN, a state whose map never changes, or a bisection that lands on one of these commits.
    7. No regression. The method decides the states early by chance (diagnosis of 2026-10-18). Signature: the anchor fails as often, and in the same way, as the current build.

    Long-standing behaviour found while reading¶

    Older than the window, present in the anchor too. Both are defects by ruling 4 and are fixed in Phase 3.

    1. In distributed runs the stage-1 references never change. The master keeps one params for the whole stage and builds the references from params%vols_even/odd, set once from the start volumes; assembly writes the new maps under other names and updates only the command line (simple_refine3D_strategy.f90, simple_matcher_refvol_utils.f90, simple_parameters_phases.f90). From stage 2 on the start volume carries the name assembly rewrites, so only stage 1 is frozen. Shared memory rebuilds params from the command line every iteration and is not affected. A note of 2026-08-23 (drop_legacy_box_division.md, section 8) saw the reference power flat over all 20 stage-1 iterations. In a distributed multi-state run this means twenty shc iterations against two noise volumes; the three-state test (shared memory) never saw it. Single-state distributed runs have the same frozen stage 1.
    2. Empty states.     Common rules¶

    • Nothing is committed; git is read-only; other commits are built from git archive exports.
    • Fix as you go. A fix that changes results waits until Phase 3, after the localisation, so that it does not move the comparisons it would confound; a defect that blocks runs (a crash) is fixed when found.
    • Thresholds are fixed before the runs they judge; never loosened, never rerun until a run passes.
    • New or changed OpenMP code gets a tester at 24 threads, repeated, compared bit for bit with one thread; no string temporaries inside parallel regions; work arrays sized by the team in use.
    • No goto; THROW macros never continued with //&; no .and. short-circuit on allocatable arrays.
    • Bulky outputs of a run are deleted once its numbers are in the journal; scratch/keep/runs/ keeps the labels, logs and final maps of every run, and scratch/keep/ the data, P2 and P2H.
