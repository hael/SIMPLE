    Single-state speed: the plan for the week of 2026-10-15¶

    Implementation note, 2026-10-14. Revised 2026-10-15 for the unattended run prob_speed on the Oracle Linux test machine, which carried out days 1 and 2 and the same changes in the 2D table (section "Execution"; the record is in "Progress" and the summary in single_state_speed_week_report.md). Days 3 to 5 are still planned. Multi-state runs added 2026-10-15 (section "Multi-state").

    Goal and baseline¶

    Make single-state solve3D/refine3D as fast as the CPU code can be for the release; GPU work follows in the next release.

    The baseline is the PfCRT run in ~/Processing/PfCRT/bench (analysis in bench_summary/analysis.md): 4,567 s, of which refinement 4,452 s, with 10 partitions of 8 threads, 16,832 particles, box 300 matched at 88-160. Every change below is measured against it with scripts/plot_refine3d_bench.py.

    The savings in this plan are estimates from that run's reports and from reading the code, not measurements. Together they come to 1,350-2,050 s, about 30-45% of the run.

    work where the time is today (PfCRT) estimated saving result
    job polling 1.0-2.0 s per polled phase, two phases per iteration 300-400 s identical
    dynamic thread scheduling in the table fill 10-17% idle threads in the fill 150-200 s statistically the same
    particle-frame shift in the prob_neigh score loop score loop at high resolution, about 580 s 400-500 s changed as prob_fast already changes prob
    exact trims in the kernels, the refinement and ref_assign shift refinement about 460 s, ref_assign 0.6-1.6 s per iteration 100-200 s identical
    nonuniform filter without the disk round trip 330 s 100-200 s identical
    reprojection model and project I/O on the master 246 s plus several project reads per iteration 50-150 s identical
    one worker process per iteration a second process, project read, reference read, particle read and preparation per iteration 250-400 s identical

    "Statistically the same" means the same algorithm with a different assignment of random draws to particles; multi-threaded runs were never bit-reproducible (simple_rnd.f90: only a one-thread run is).

    Rulings of 2026-10-15¶

    • prob_fast is retired. Its runs validated in 3D, and the same change will work in 2D. Its particle-frame paths become the only paths, in the prob and prob_neigh tables and in the 2D table; the key goes from the parameters, the parser and every user interface, and code reached only with prob_fast=no is deleted.
    • The 2D table gets the same changes in the same run (section "The 2D table").
    • Gains measured on the test machine are reported. These changes are compute-bound, so beta-galactosidase timings there are meaningful; PfCRT is measured by the maintainer afterwards.
    • The distributed simulated test is a second solve3D step with nparts=2 in simulated_workflow_1jxy, added as checks to that suite (no new CTest entry).
    • After the Phase 3 stop: the 2D particle-frame shift stays; simulated_workflow_6vxx runs with its own root seed, 20261003, and simulated_workflow_1jxy keeps 20260923 (floors unchanged); the crash of solve3D's map symmetrization on very small data is fixed in this run (Progress, Phase 3).

    Testing procedure¶

    The work is tested in three blocks. Each block is checked on the simulated high-level tests first, and only then on one PfCRT run:

    block simulated tests then
    days 1 and 2, the 2D table after each item, with beta-galactosidase timings (the run prob_speed) one PfCRT run for the block
    days 3 and 4 after each item one PfCRT run for the block
    day 5 after the item one PfCRT run, and the dataset with one stack per micrograph

    The simulated tests are the high-level CTest entries with a simulation truth (ctest -L highlevel):

    • simulated_workflow_6vxx and simulated_workflow_1jxy: solve3D on simulated movies, the final map checked against the truth (correlation and masked FSC). They run on one thread with SIMPLE_SEED set, so their outputs are reproducible: an identical change must leave their maps and orientations byte-identical.
    • solve3D_addon: solve3D on simulated particles on eight threads, poses and map checked against the truth. This one exercises the dynamic scheduling.
    • cont_refine3D_1jxy: the only one that runs distributed (nparts), but with refine=cont, not the probabilistic tables.

    The distributed gap. simulated_workflow and solve3D_addon run solve3D without nparts, so they take the shared-memory strategy, where the table and the search run in the master process. The job polling (day 1), the redundant segment write and the reprojection model (days 1 and 4) and the worker fold (day 5) are only on the distributed path. simulated_workflow_1jxy therefore gets a second solve3D step with nparts=2 on the same project (ruled 2026-10-15), whose final map must pass the same truth checks as the shared-memory step.

    What passing means:

    • One diff per work item, reviewed and compiled on its own; the fast gate passes.
    • Identical changes: byte-identical outputs of the two simulated_workflow suites before and after.
    • Changed results: every simulated test keeps passing its truth checks, with the truth metrics recorded before and after. At the block's PfCRT run, the FSC 0.143 resolution stays within the run-to-run spread.
    • Timing: the simulated tests are too small to time; the saving of a block is measured at its PfCRT run, read with the summary script, and recorded per block in the progress section of this note.

    The particle I/O run, which edited the same matcher and prob files, finished on 2026-10-15; its changes are merged before the run prob_speed starts.

    Day 1: measurement and the identical fixes on the master¶

    1. Benchmark layout and the missing report. Compile the BENCH/ change (one appended file per report family). Add timers and the PROB_ALIGN report to exec_prob_align_neigh, which writes none, so the prob_neigh pre-step can be split like the prob one.
    2. Job polling (src/utils/qsys/simple_qsys_ctrl.f90, schedule_jobs and schedule_array_jobs).
    3. The loop tests the done flags before refreshing them and then sleeps a whole second, so the master always waits 1 to 2 s after the last part has finished. Refresh before the test.
    4. Poll every 100-200 ms with the existing c_usleep binding (src/extlibs/unix/src/unix_unistd.F90, already used with 100 ms in simple_forked_process.f90). Keep one second on batch queues, where the done files sit on a shared file system.
    5. Redundant project write. The strategy writes the project segment before prob_align (simple_refine3D_strategy.f90, about line 1310) although nothing changed it since the read just above. Remove it.
    6. Dynamic scheduling in the table fill. The single-state prob loop (simple_eul_prob_tab.f90, about line 281) and the prob_neigh loops (simple_eul_prob_tab_neigh.f90, about lines 188, 199, 402, 412) are static. The multi-state prob_fast loop is already dynamic, with the measured gain (load balance 0.90 to 0.98) in its comment. Each particle is processed whole by one thread, so only the random draw a particle gets changes.

    Test: the simulated tests after each item. Expected on PfCRT: 450-600 s less, measured at the block's PfCRT run after day 2.

    Day 2: the particle-frame shift in prob_neigh¶

    At 5,000 directions the prob_neigh score loop is the largest single item. For single-state runs it shifts the reference for every scored reference: it rebuilds the shift matrix in double precision and runs one forward FFT per shell, about 530 references per particle. The prob table with prob_fast shifts the particle once (memoize_shifted_ptcl) and scores every reference against the unshifted memoized references (gen_likelihood_val_bank). The neighbourhood table never reads prob_fast.

    • Port the same path to the neighbourhood fill: memoize the shifted particle after the seed, score with the bank kernel in the coarse and the fine passes, start the refinement from the converted shift (shift_ptcl2ref), and record the seed in ref_assign_neigh. Unconditionally: there is no key.
    • Retire prob_fast (ruling of 2026-10-15): its paths in the prob table (the single-state particle-frame seed; the multi-state particle-frame grid and its quadratic step) become unconditional; the key leaves simple_parameters.f90, the parser, the refine3D and solve3D-family interfaces and the table part's benchmark lines; code reached only with prob_fast=no is deleted, and testers that compared the two paths test the remaining one.
    • Estimated 3-5 times faster score loop: 400-500 s on PfCRT.
    • Validation as for prob_fast: the same semantics (a particle-frame shift, the angular Nyquist bin included) already accepted for prob.

    Test: the simulated tests, then the PfCRT run for days 1 and 2. Expected: 850-1,100 s less than the baseline.

    The 2D table: the same changes¶

    The 2D table (simple_eul_prob_tab2D.f90) does per particle what the neighbourhood table does: it estimates one shift at the previously assigned class, scores every class with that shift through the shifted-reference kernel (a shift matrix and one forward FFT per shell for every class), and refines the shifts of a few classes around the best one. Both fill paths do this, the plain table (fill_tab_range, used by refine=prob and the solve2D seed pass) and fill_tab_prob_snhc_range (the prob_snhc stages solve2D runs by default).

    1. Benchmark first. The 2D table part's report has wall times but no thread-seconds split; give it the fill profile the 3D tables write (seed estimation, score loop, refinement, fill wall time, load balance).
    2. The particle-frame shift in both fill paths: shift the particle once after the seed and score every class with the bank kernel; record the seed as the 3D table does.
    3. Dynamic scheduling of the 2D fill loops (about lines 253, 305, 366 and 376 today).

    A 2D table scores every class for every particle (often 100-500 classes), so the score loop should gain as much as in 3D; how much of solve2D that is, the benchmark of item 1 tells.

    Day 3: exact trims in the table, the refinement and the assignment¶

    1. Shift refinement (the prob stages; src/main/pftc/simple_polarft_corr.f90): every cost or gradient evaluation copies the reference to double precision, twice in the gen_corr_grad_only_for_rot_8 path, and rebuilds the shift matrix with its sines and cosines. Copy the reference once per minimization; build the matrix from the shift without the second copy.
    2. The shift matrix range (simple_polarft_geom.f90): the conversion to single precision covers the shells up to interpklim (about box_crop/2) instead of the searched kfromto. Convert only the searched shells.
    3. ref_assign for prob (simple_eul_prob_tab.f90, about lines 592-600): every assignment scans all particles (any(ptcl_avail)) and advances the head of every reference. Count the available particles and advance only the references whose head was the assigned particle, as the neighbourhood version already does. Carried out with the multi-state ref_assign by the run ms_speed.
    4. Neighbourhood table read (read_tabs_to_glob): every part's file is opened and read twice, serially. Read it once, counting and filling in one pass. Carried out with the parallel reads of the prob table by the run ms_speed.
    5. Score-loop profile at high resolution. The cost per reference at shell 78 and box 160 is about twice what the shells and the box explain. The likely cause is the reference memo (about 4 GB at 5,000 directions) streaming from memory for about 530 scattered references per particle. Profile one table part (perf counters, or two shell limits at the same number of directions) and decide whether to reorder the work, for example blocking particles by neighbourhood so threads share references.
    6. Single-precision weights in the score kernels (gen_euclid_crvec and its bank version multiply single-precision data by a double-precision weight, which halves the vector width). Rounding-level change: implement, measure, keep only with the FSC check.

    Test: the simulated tests after each item; items 1 to 4 must leave the simulated_workflow outputs byte-identical.

    Day 4: the master's serial work¶

    1. Nonuniform filter (src/main/nu_filt/simple_nu_filter_state.f90, cache_filtered_vols, and simple_nu_filter_bank.f90, setup_nu_dmats): every candidate low-pass (up to 8, cut at the FSC) writes the filtered even and odd volumes to disk as MRC; the objective reads them back, and the final composition by label (simple_nu_filter_apply.f90) reads them a third time.
    2. Not by keeping them in memory: 2 x candidates x box^3 x 4 bytes, up to 0.26 GB at box 160 but 1.7 GB at box 300 and 8.6 GB at box 512 in the final pass, about twice the filter's present peak.
    3. Instead, without extra memory: compute the objective right after filtering each candidate (one pair alive at a time), and in the composition filter each candidate again from the Fourier transforms of the two input volumes (a multiply and two inverse FFTs per candidate) instead of reading it. Same numbers, no disk traffic.
    4. First split the 6.6 s per iteration with timers; then try the candidate loop in parallel where memory allows.
    5. Reprojection model (materialize_reprojection_model, simple_refine3D_strategy.f90, about lines 523-551): every iteration builds a new builder, reads the whole project and builds the toolboxes before projecting. Keep one reference builder in the strategy for the run; the projection itself is already parallel.
    6. Project reads. prob_align and volume assembly each read the project again although the master holds it in memory (volume assembly reads the particle segment twice). Hand them the in-memory project. The cost grows with the particle count: small on PfCRT, large on a 750,000-particle project.

    Test: the simulated tests, then the PfCRT run for days 3 and 4. Expected: 250-550 s less than the run after day 2.

    Day 5 and the next week: one worker process per iteration¶

    The prob_tab part and the search worker are two processes per partition and iteration, separated by the master's ref_assign. The second one reads the project, the reprojection model and the particles again and prepares the particles again. Both use the same sample, batch formula, shells, crop and particle preparation.

    • One worker per partition: fill the particle buffer, prepare the references, fill and write its table part, signal "table written", wait for the master's assignment, then search and reconstruct with the references and particles it already holds.
    • The master: wait for the "table written" files, read the tables, run ref_assign, publish the assignment by writing a temporary file and renaming it, then wait for the done files.
    • The worker waits with a sub-second c_usleep loop.
    • Check before starting: prob_align and refine3D build their partitions through different qenv%new calls; their first and last particles per part must be identical.
    • Peak memory per worker rises: the table, the memoized references and the particle buffer are live together (the table part alone peaked at 0.6-0.7 GB on PfCRT); the memory policy's budget must cover it.
    • Design and the partition check on day 5; implementation and validation the following week, behind the old path until the simulated tests (the distributed run among them), the PfCRT run and the per-micrograph dataset pass.

    Execution: the run prob_speed¶

    Days 1 and 2 and the 2D table are carried out as an unattended run on the Oracle Linux test machine (arun run prob_speed), in five phases. Nothing is committed; the maintainer reviews the complete diff. Every phase records itself in the progress section.

    Common to every phase:

    • Data. Beta-galactosidase (5,513 particles, box 256 at 1.275 Å per pixel, mskdiam=180 pgrp=d2), copied into a fresh directory under the run's scratch directory for each run; the originals are never written.
    • Execution settings. nparts=4 nthr=6 for distributed runs and nthr=24 for shared-memory runs, identical in every phase. Timed runs use an out-of-tree Release build with tests built; nothing else heavy runs while a run is timed.
    • Timing (ruled 2026-10-15). Gains are reported.     Baseline¶

    The baseline is the three-state solve3D run in ~/Processing/msp1/bench (analysis in bench_summary/analysis.md; its per-iteration reports converted to BENCH/, the originals kept): 10,415 s for 141,838 particles, 30,012 of them searched per iteration, three independent states, box 288 matched at 88-160, 5 partitions of 16 threads. The default multi-state schedule: shc in stages 1 and 2, prob in stages 3 to 5 (2,500 directions in stage 5). The run used the multi-state table as it was before its particle-frame grid.

    What differs from single state:

    • The table is 68% of the run (43% on PfCRT). Every particle is scored against every direction of every state (7,500 references in stage 5) at zero shift, because independent states share no shift frame.
    • In stage 5, two thirds of the fill's thread time is the shift refinement: 138 refined references per particle, each with a 5 x 5 grid over every in-plane rotation and then L-BFGS-B.
    • The table is dense, 28 bytes per particle and reference in the files. In stage 5 that is 6.3 GB written by the parts and read serially by the master every iteration, and 5.4 GB held by the master (peak 8.0 GB).
    • ref_assign labels the states and then assigns within each state on one thread, rescanning every reference and particle per assigned particle: 8.6 s per iteration in stage 5.
    • shc stops at the first better reference. As the maps settle it scans most of the 3,000 references: 1 s per part in iteration 1, 26-28 s at the end of stage 2.

    What the run prob_speed brings¶

    Retiring prob_fast makes the multi-state table always build the coarse grid from 25 shifted copies of the particle, made once per particle and shared by all its refined references. Where the grid fit holds, a quadratic step replaces L-BFGS-B. The fill is scheduled dynamically, and the job polling is faster.

    On the two-state bgal refine3D test of 14 October this cut the refinement 3.4 times, from 141 to 41 thread-seconds, and the table step from 34 to 15 s. Applied to msp1, it is estimated to save about 3,250 s in the tables and 150-200 s in polling, taking the run from 10,415 s to about 7,000 s. No multi-state run has measured it yet. The first measurement is msp1 after the merge (maintainer), plus case M below.

    Rulings of 2026-10-15 (multi-state)¶

    • prob_neigh in its state mode from 2,500 directions. A multi-state run switches from prob to prob_neigh (state) at the first stage whose directions go from 1,000 to 2,500. In the default schedule that is stage 5, which so far ran prob over every direction of every state.
    • Directions capped at 2,500 in multi-state runs. Stages 7 and 8 of the eight-stage table, 5,000 directions today, stay at 2,500.
    • shc leaves stage 2 once it scans more than 95% of the search space on average, whatever the state overlap. The measure is the mean over the particles of the percentage of references the search scanned, which it stores per particle as frac and the log prints as "% SEARCH SPACE SCANNED".
    • refine3D_states is capped at 2,500 directions too (ruled later on 2026-10-15). Its prob_neigh stage ran at 5,000 directions (STAGE2_NSPACE). The ruling caps the directions only; its 500 subspace directions (STAGE2_NSPACE_SUB) stay.
    • Still open: a cap on the refined references per particle across states (138 of 7,500 in msp1's stage 5).

    These rulings change solve3D's multi-state schedule and refine3D_states. solve3D's particle route and its class-average route share the mode policy, so both switch at stage 5. The stage-2 exit concerns the particle route, the only one with shc stages. The run ms_speed carries them out (multistate_speed_run.md, beside this plan).
