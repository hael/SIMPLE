    Continuous Cartesian pose refinement (refine=cont): refactoring plan¶

    • Status: completed by the delegated run (section 14.1), Phases 0 to 10 done (section 15), awaiting the maintainer's review of the raw diff; O4-O8 taken as recorded under "Delegation", each open to reversal at review; doc/code_overview/fortran-indexes to be regenerated by the maintainer (Phase 10 row)
    • Scope: five-parameter Cartesian pose refinement and its integration in refine3D and refine3D_auto
    • Source baseline: the inventory was taken at master 712b4d86 and still holds at 30d23bc62 (line counts, the matcher line numbers of section 8.1 and the parameter lines cited in Phase 1 are unchanged). Phase 0 records its numbers at the commit the refactoring branches from, not at 712b4d86 (Phase 0)
    • Last updated: 2026-10-01

    This document is self-contained. It holds the contract, the current-state inventory, the target architecture, the phased refactoring, and the test plan. Per repository policy the maintainer compiles and runs; the delegated run of section 14.1 compiles and runs on the Dell under the maintainer's request.

    1. Goal¶

    Give continuous Cartesian pose refinement the same boundaries as the rest of SIMPLE:

    • refine=cont is a refinement mode of refine3D that runs with no polar object alive, and refine3D_auto accepts it;
    • the matcher references exactly one continuous-pose symbol, strategy3D_cont;
    • the numerics sit in two encapsulated classes, a calculator owned by builder and an optimizer owned by the strategy, as in the polar path;
    • both objectives follow objfun with the polar definitions, and the reference follows the polar branch;
    • a pose polish after discrete search is available as a scheduled Cartesian pass;
    • there is no separate refine3D_pose_cont program.

    Two rules hold for the whole sequence. Ownership moves and scientific changes are separate commits; Phase 3 is the only phase that changes numerics. Existing tests are reused and moved with the code they test; every new behavior lands with its test in the same phase (section 10).

    What is wrong with it:

    1. The matcher hosts two continuous-pose pipelines (pose_cont=yes after a discrete winner, refine=pose_cont instead of the search). 124 of its 717 lines mention continuous-pose state; it holds the only three select type downcasts in non-test strategy code and a 55-line numerical routine (section 8.1).
    2. The adapter exports eleven public types and nine free procedures and has no type named after the module. Most procedures forward to the refiner or wrap one or two image/ori calls (section 8.2).
    3. strategy3D_pose_cont cannot satisfy the strategy3D contract: the base embeds the PFTC search object s, which it never initialises, and it needs a seven-argument bind_context and a get_result that are not in the abstract interface.
    4. The objective ignores objfun: both euclid and cc runs optimize a normalized correlation on sigma-whitened data. corr is never written.
    5. Shared helpers import the adapter and take optional feature flags (cartesian_only, pose_cont_particles); euclid_sigma2 gained a second constructor and a setter that lets an outside module write sigma2_part.
    6. Parameters: four switches, string comparisons in four modules, validation keyed on a program name, cc_emit_sigma silently forced on, LM policy hard-coded in adapter type defaults.
    7. The particle record grew from 50 to 52 reals for two telemetry flags.
    8. Reporting exists three times: per-particle fields, a stats module with its own per-partition files, and system_clock timers in the particle loop.
    9. commander_refine3D_auto was given four override hooks so that a second commander could inherit from it.
    10. 28 error stop statements in the continuous-pose code (24 in the refiner, 4 in the adapter), several reachable from the OpenMP particle loop; four of them sit in pure procedures (sample_fourier_with_grad, shift_native_to_crop, shift_crop_to_native). The four in simple_cartesian_fourier (shape checks in center_embed_real3d and center_crop_real3d) belong to the shared layer and are out of scope.

    What is sound and is kept: rollback to the input pose after a failed solve; explicit shift and rotation bounds anchored at the seed; explicit even/odd reference selection; the KB derivative in simple_kbinterpol; the stateless simple_cartesian_fourier layer; the numerical tests.

    3. Contract¶

    Accepted by the maintainer on 2026-09-30.

    Id Ruling
    C1 The matcher uses one strategy object, strategy3D_cont, and no other continuous-pose symbol.
    C2 simple_pose_cont_refine3D_adapter is dissolved; each piece moves to its owner.
    C3 The feature is restructured as encapsulated classes: private components, new/kill, type-bound behavior, one type per module named after it.
    C4 Both objectives are supported and follow objfun, mirroring the polar implementation.
    C5 sigma2 is never part of a correlation calculation. A Cartesian cc pass neither reads, requires nor writes sigma2, as in the polar branch, where sigma2 is not produced under objfun=cc (ruling 2026-09-30). The internal cc_emit_sigma of the polar CC pose initialization does not apply to Cartesian passes.
    C6 Cartesian euclid is the polar loss, normalized by the particle's weighted power, with exp(-L) as the stored score.
    C7 refine=cont is a refinement mode of refine3D, testable on its own and independent of the polar machinery.
    C8 Pose polishing after discrete search is supported. It is scheduled per pass: a refine=cont pass follows a discrete pass. A per-particle second stage inside one pass is not part of this plan; it can be added later on the same objects.
    C9 The Cartesian and polar objectives are not directly comparable. No decision compares a value from one with a value from the other.
    C10 The reference follows the polar branch of refine3D, including how deapodization is handled.
    C11 refine3D_auto supports refine=cont. In that mode it bypasses all polar machinery, including the discrete greedy initialization, and runs a purely Cartesian refinement. It is therefore a continuation mode: the project must already hold 3D poses from a discrete workflow.
    C12 refine=cont in refine3D_auto follows the nsample policy.
    C13 refine3D_pose_cont is not a separate program.
    C14 Each representation persists its own objective value: polar passes write corr, Cartesian passes write corr_cart. A Cartesian pass never writes corr. Stored scores are read, not recalculated by the code that needs them (ruling 2026-09-30; replaces "the refined Cartesian score is persisted in corr").
    C15 The particle record carries corr_cart and the improved flag; "attempted" equals "sampled in a Cartesian pass" and needs no field. The layout is O8 (the 50-real target accepted earlier cannot hold the extra field and is superseded).
    C16 One LM route is kept, chosen from the Phase 0 baseline; pose_cont_route is removed and LM policy becomes private constants of the optimizer.
    C17 Names: folder src/main/cftc, classes cartft_calc and cartft_pose_opt, builder field cftc, and an abstract strategy3D_pftc parent for the polar strategies. New identifiers use the short form cart for Cartesian (modules, types, procedures, variables, files, suite= selectors); prose keeps "Cartesian" (2026-09-30).
    C18 The end-to-end gate gets its own high-level CTest entry, cont_refine3D_1jxy; SIMPLE_CTEST_BUDGET goes from 29 to 30.
    C19 The polish switch is pose_cont=yes\|no. When on, a Cartesian pass follows every discrete iteration, in refine3D and in refine3D_auto.
    C20 refine3D_auto keeps objfun=euclid; objfun=cc with refine=cont is available through refine3D only.
    C21 objfun_den with refine=cont is rejected in parameter validation for now.
    C22 The Cartesian references reach the matcher as a file of prepared real-space volumes, written once per iteration by the reference materializer and read by every matcher, shared-memory or distributed. The matcher pads and transforms them and gathers central sections on the fly; it does not prepare references itself (accepted 2026-09-30; section 6.6).

    Facts verified in the source that the contract relies on:

    • C10. The polar branch prepares the reference in read_mask_filter_refvols, pads it by 2 in real space (pad_fft), expands it (expand_cmat) and gathers with normalized KB weights scaled by pf^3 (interp_fcomp_oversamp). It applies no inverse KB envelope at the gather; deapodization happens when the volume is reconstructed (reconstructor%invenv1d). The Cartesian production path (new_physical_reference) already does the same on the same prepared volume, and test_matched_projector_boundary pins its gather against interp_fcomp_oversamp. The unused new_inverse_envelope_reference is removed unless O5 is ruled (b). The polar branch also passes the particle through the same stencil (polarize_oversamp); the Cartesian particle side is O5.
    • C14. With corr_cart beside corr, the two representations never share a field: a Cartesian pass writes corr_cart for every particle it processes, accepted or not, and leaves corr as the last polar pass left it. Under pose_cont=yes, corr therefore refers to the discrete pose before the polish and corr_cart to the polished pose; under refine=cont, corr keeps the value of the discrete workflow the poses came from. Within corr, scores from different iterations and band limits still sit side by side under fractional updates, as they always have. The readers of corr, all of which now see polar values only:
    • The one routine that sorts the stored ptcl3D score is make_projdir_class_samples in refine3D_states (balance=yes with fractional updates); it orders each projection bin by corr. sample4update_class reads that order only to cut a bin to its best frac_best fraction, or to take its top nsample under greedy_sampling=yes. exec_refine3D_states sets frac_best=1.0 and greedy_sampling=no unconditionally, so the whole bin is eligible and the sample is drawn by lowest updatecnt with a shuffle: the order is never read. The final missing-update pass runs with balance=no.
    • The class-biased sampling of abinitio3D, classify3D_refs, sample_classes and bootstrap_cavgs ranks ptcl2D scores, which a Cartesian pass does not write.
    • The even/odd choice in abinitio3D_cavgs compares two polar scores of one run. gen_ptcl_mask (with frac_best), extremal_bound and get_proj_sample_stats rank corr but have no production caller.
    • Every other reader is a report (convergence statistics, the class document of cavger_gen2Dclassdoc, the abinitio3D_addon report) or tests corr against zero (has_been_searched).

    The reader of corr_cart is the per-iteration report of a Cartesian pass (simple_convergence, over the particles that pass sampled). No consumer recalculates a stored score. - C15. simple_binoris%read_particle_record reads records narrower than the current width and is pinned by test_legacy_narrow_particle_records. It rejects wider ones. The record is 52 reals since 2026-09-21: slot 51 holds pose_cont_attempted, slot 52 pose_cont_improved, both 0/1, cleared by the matcher on every run, so only particles of a pose_cont run carry a 1. Slot 42 (cc_nonpeak) is unused today but carried a correlation statistic in earlier versions (its reporting was removed in e45fd1aa2, 2024-03-19), so older projects can hold values there. - C10, the reference handoff. No central section is precomputed on the Cartesian path. materialize_reprojection_model_from_volumes, in the iteration strategy, runs the reference preparation the polar branch runs (read_mask_filter_refvols: volume choice, masking, filtering, envelope; the low-resolution even/odd blend; centering, with its shift mapped into the project) and writes the prepared real-space volumes, one MRC file per state and half (pose_cont_reference_stateNN_{even,odd}.mrc). Under refine=pose_cont (cartesian_only) it skips the reprojection; under pose_cont=yes it reprojects as well. The matcher reads them (load_reference_slot), pads each by 2, Fourier transforms it once (load_pose_reference) and extracts every Fourier sample it needs at the continuous rotation by a KB gather with derivatives (sample_fourier_with_grad). What crosses the boundary is the prepared volume, not a reprojection model. The handoff stays because the preparation and the band limit are decided once, by the strategy (refine3D_policy.md, section 6), for every matcher of the iteration (section 6.6); its ownership moves (section 6.4).

    6.6 Prepared reference volumes: the handoff file contract¶

    The Cartesian path hands the matcher volumes, not projections. For each state and half the file holds the prepared real-space volume, the one the polar branch pads and reprojects over its grid. The calculator pads and transforms it once when it reads it and gathers each Fourier sample at the continuous rotation during the solve (section 6.2).

    Why a file at all: the preparation (volume choice, masking, filtering, envelope, low-resolution even/odd blend, centering with its shift mapped into the project) and the band limit (set_bp_range3D, estimate_lp_from_refs) are decided once, by the iteration strategy, before any matcher runs (refine3D_policy.md, section 6). Every matcher of the iteration, shared-memory or distributed, then reads the same references and the same band. With pose_cont=yes the discrete and the Cartesian passes of one iteration see one preparation by construction.

    Alternative not taken (C22): each matcher prepares its references from the state volumes. The preparation and the band-limit decision would then run once per partition; the band limit and the centering shift would need another channel to the workers (the project mutation of centering must stay on the master); and the polar and Cartesian references of one iteration would come from two preparations. It saves a file of nstates * box_crop^3 * 4 bytes per half, written once and read once per partition, far less than the particle images each partition reads.

    7.2 Convergence (open, O2)¶

    • The single-state rule in check_conv3D is frac_srch%avg > 99 .and. mi_proj > overlap, gated by minits. refine3D_auto sets overlap=0.99.
    • Per particle, mi_proj is 1 when the symmetry-aware angular distance between the previous and the new orientation is at most angthres_mi_proj (default 2 degrees). It is not tied to the discrete grid.
    • A local optimizer reports frac=100, as deterministic neighbourhood refinement already does, so the frac gate is always met.
    • Under refine=cont the rule therefore reduces to "99% of the updated particles moved less than 2 degrees", which a pass that only removes grid error could meet at once, and it ignores shifts.
    • Precedent for a motion-based rule: 2D refine=inpl converges on dist_inpl%avg < 0.5.

    Interim rule until O2 is decided: check_conv3D does not declare convergence under refine=cont. A run goes to maxits, which refine3D_auto derives from the target number of updates per particle. minits would only delay the faulty decision. With pose_cont=yes in a discrete mode the rule is unchanged, because the polish leaves the discrete search's convergence fields in place (Phase 9).

    Candidates to evaluate on the logged statistics: an angular threshold derived from the current resolution and mask diameter (the registration pass already computes res / (mskdiam/2)); a rule on mean orientation and shift motion (dist, shincarg); the fraction of improved particles falling below a floor (an FSC plateau was listed here; ruling R5 removes the FSC from validation).

    10. Test plan¶

    10.1 Principles¶

    From doc/policies/test_environment_policy.md:

    • A test asserts through simple_test_utils, derives its expected value independently of the code under test, names its tolerances, fixes its seeds, and pins sign, handedness and index conventions.
    • A unit test is a routine in simple_<thing>_tester.f90 beside the code it tests, exporting one run_all_<thing>_tests, registered as a sub-suite in simple_commanders_test_class.f90 and listed in the suite= help of simple_test_ui_class.f90.
    • Fast tier: hermetic, in-process, one thread, each sub-suite well under a second, whole gate under 30 s. Library tier: the same rules at realistic size. High-level tier: a pipeline on simulated data, gated against the simulation truth with declared floors and a metrics.tsv.
    • A new CTest entry is an owner decision; the one new entry of this plan is accepted (C18).

    Specific to this refactoring:

    • An existing test is moved, not rewritten, when its guarantee still holds. It moves in the same commit as the code it tests.
    • While a forwarder exists (Phases 2-6), the old tester keeps running against it. That is the parity proof for the move.
    • A test is retired only when its subject is deleted or its guarantee is replaced by a decision in section 3. The commit names the reason and the replacing test.
    • A new behavior is not complete until its test is in the same phase. No phase exits on manual inspection alone.
    • Cross-representation tests compare optima and physical quantities, never raw objective values (C9).
    • A floor is never taken from the first run of the code being accepted. It comes from the simulation truth (the error must fall by a stated factor relative to the injected error), from an analytic bound (the rotation error must end below the basin width at the band limit, lp / (mskdiam/2) radians), or from the pre-refactor implementation measured at Phase 0 on the same fixture, with a stated margin.
    • Ruling R5 (2026-10-01, recorded in Phase 8; amended the same day, recorded in Phase 10): the FSC counts only at a scale where it means something. For small tests on noisy particles (2 000 particles or fewer, E25 at 1 000, the N20 gate, N29) the FSC is no criterion; correctness is verified against the ground-truth orientations (rotation and shift error, RMS and median, before and after; fraction within the basin width; accept fraction), and every FSC floor, FSC comparison with Phase 0 and FSC-triggered rerun is dropped for them, including the FSC entries of E25's floors and of any polar guard of 2 000 particles or fewer. At larger scale (more than 2 000 particles) the FSC may serve as a criterion where the plan uses one: to the truth on simulated data, the half-map FSC on the beta-gal set (5 513 particles).     14. Unattended execution¶

    A phase may be run unattended, for example by a scheduled overnight Claude Code run. The rules below add to sections 9-11 and relax none of them.

    • A run carries out one phase, or the part of a phase up to its review checkpoint, and stops there. It never starts the next phase.
    • It works in its own worktree, on its own branch from the last accepted phase. It does not push, merge or rebase.
    • Its prompt is the explicit request for builds and tests that repository policy requires. The prompt names ./compile_debug.sh, scripts/run_fast_gate.sh, the checks of section 11 and the CTest entries of the phase; nothing else is compiled or run.
    • It edits only the files section 8.3 assigns to the phase. The runner enforces the file list and the command list mechanically, not by instruction alone.
