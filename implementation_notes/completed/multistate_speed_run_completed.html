    Multi-state speed: the run ms_speed¶

    Implementation note, 2026-10-15. The execution plan of the unattended run ms_speed on the Oracle Linux test machine. The design is in single_state_speed_week_completed.md (beside this note): its section "Multi-state" (the rulings and items 1 to 3) and items 3 and 4 of its section "Day 3". This note holds the run's work, cases, rules, phases and progress.

    Status, 2026-10-20: split. Done: Phase 0 (baseline), Phase 1 (the multi-state schedule, accepted by the maintainer's ruling of 2026-10-16), Phase 2 (ref_assign without rescans: implemented and identical on the tester and on one-thread runs; it stopped at two noisy multi-threaded checks, and the code is applied in the tree), and Phase 3 (table reads, carried out by the run speed_mac, see identical_speed_run.md). Open: the ruling on the Phase 2 stop, and Phase 4 (documents, final runs, the report). They are in ../planned/multistate_speed_run_unfinished.md. Where the text below says "plan" or "nothing implemented", read it with this status.

    Goal¶

    Make multi-state runs faster for the release; multi-state matters even more than single state (maintainer, 2026-10-15). The baseline is the three-state msp1 run (141,838 particles, analysis in ~/Processing/msp1/bench/bench_summary/analysis.md): 10,415 s before the run prob_speed. That run is estimated to bring it to about 7,000 s, and the work of this run to about 5,000 s; these are estimates from msp1's reports, not measurements. This run measures the gains on beta-galactosidase; the maintainer measures msp1 afterwards.

    The work¶

    1. The multi-state schedule (rulings of 2026-10-15; results change):
    2. A multi-state solve3D switches from prob to prob_neigh with prob_neigh_mode=state at the first stage whose directions go from 1,000 to 2,500. In the default schedule that is stage 5; the switch is derived from the stage table of directions (NSPACE), not from a second stage constant. NSTAGES_INDEPENDENT keeps the default stop after stage 5 with a definition of its own.
    3. Directions are capped at 2,500 in multi-state solve3D runs (stages 7 and 8, 5,000 today, when a user runs them) and in refine3D_states, whose prob_neigh stage ran at 5,000 (STAGE2_NSPACE). Its 500 subspace directions (STAGE2_NSPACE_SUB) stay.
    4. Stage 2 of a multi-state solve3D ends once shc scans more than 95% of the search space on average, whatever the state overlap. The present rule (state overlap and scan together) still ends it earlier if it is met. Stage 1 and every other user of the multi-state rule stay as they are.
      • The measure is the mean over the particles of the percentage of references scanned, which the search stores per particle as frac and the log prints as "% SEARCH SPACE SCANNED".
      • The controller tells the rule through an internal key on stage 2's refine3D command line, set together with fracsrch=95. The key is declared like cohort_sampling: parameters and parser, marked internal, no interface entry.
    5. The strategy's benchmark report (REFINE3D_STRATEGY) records the mean percentage scanned, and the summary script shows it.
    6. ref_assign without rescans (identical results), in the dense table's assignment:
    7. Single state: count the available particles instead of testing all of them (any(ptcl_avail)) for every assignment. Advance only the references whose head was the assigned particle, as the neighbourhood assignment already does.
    8. Several states: the state labels come from a global greedy frontier, and a particle leaves it at its smallest distance over all references. So its label is the state of its best reference. Compute that per particle, in parallel.
    9. The two agree except when two references of different states tie exactly for a particle's minimum, for example a flat particle whose distances are all equal. The tie rule is the lowest reference index, written in the code and tested.
    10. Within a state: loop over that state's references only, count the available particles, and advance only the heads that pointed at the assigned particle. The random draws and their order are unchanged.
    11. Table reads (identical results):
    12. The prob driver reads the part files in parallel; each part fills only its own particles' columns of the master table. The master table is not initialised in full, since every entry is overwritten and the read already stops on an incomplete part.
    13. The neighbourhood table (read_tabs_to_glob of the prob_neigh table) reads each part file once, counting and filling in one pass, instead of twice.

    The neighbourhood assignment (ref_assign_neigh), which stage 5 of a multi-state run uses after item 1, already works on a sparse graph with counters and is not changed.

    Common rules¶

    • Data. Beta-galactosidase: /data2/bgal_addon/control/bgal_addon.simple (5,513 particles, box 256 at 1.275 Å per pixel, the 2D classification, mskdiam=180 pgrp=d2). It is copied into a fresh directory under the run's scratch directory for each run; the originals are never written.
    • Builds. Timed runs use an out-of-tree Release build with tests built. The gates use the Debug build of ./compile_debug.sh, which runs the fast gate.
    • Execution settings. nparts=4 nthr=6 for distributed runs and nthr=24 for shared-memory runs, identical in every phase. One case at a time on the otherwise idle machine.
    • Timing. Gains are reported as numbers from this machine.
    • Every timed comparison is the same case before and after, at least twice each way, interleaved, read with scripts/plot_refine3d_bench.py: wall time, the critical path per iteration, the table parts' thread-seconds, and the pre-step driver's table reads and ref_assign.
    • The long case MS-shc runs once each way.
    • A change is kept unless it is slower than the build without it beyond the run-to-run spread.

    Acceptance.

    • Single-state paths in every phase:

The run identifier in solve3D_manifest.txt and the layout digest in the header of sigma2_state.bin hash absolute paths, so they are ignored.

    • solve3D_addon and cont_refine3D_1jxy pass.
    • Identical changes (phases 2 and 3):
    • The 3D table tester compares the new assignment with the present one, kept in the tester as the reference, on synthetic dense tables of one and of three states with a fixed seed. The assignments are identical, and the tie case follows the written rule.
    • M's state populations and last-iteration mean score stay within the spread of the before-runs; multi-threaded runs are not bit-identical.
    • The schedule change (Phase 1):
    • MS and MS-shc run to the end, and every state keeps particles and a map.
    • Each state's final FSC 0.143 and population are recorded against Phase 0. The earlier rule (no worse than 1.05 times the worst state of Phase 0) was dropped by the maintainer's ruling of 2026-10-16, after Phase 1: on beta-galactosidase the states that missed it are noise classes of a dataset without real states, and the schedule is judged on msp1. A multi-state case is accepted when it runs to the end and every state keeps particles and a map.
    • MS-shc's stage 2 ends by the 95% rule: record the iteration and the percentage, against Phase 0's stage-2 length.
    • flex_pca_blobs and solve3D_pyramid_blobs pass their checks (or do no worse than on the base, if the base already fails one).
    • If a multi-state check fails, stop and describe it: the maintainer decides with msp1.
    • Gates. The fast gate (./compile_debug.sh), the CTest unit suites of the touched areas, and python3 scripts/check_test_registry.py . whenever tests or their registration change.

    Phases¶

    Phase 0: baseline¶

    1. Build the tree as it is: the Debug build with the fast gate, and the Release build for timed runs, kept for the before-runs of Phase 1.
    2. Run the cases on the Release build:
    3. S1 and S3, kept;
    4. A twice, MS twice, M twice, MS-shc once.
    5. Record for every case:
      • the exact command line and the wall time;
      • the final FSC 0.5 and 0.143 per state, and the state populations;
      • the summary script's report; keep its benchmark reports.
    6. Record MS's list of stages (refine mode, directions, iterations), and MS-shc's stage-2 length and the percentage scanned at its last iteration.
    7. Run the tests on the Release build, keeping the outputs of the two simulated_workflow suites for the byte comparisons:
    8. simulated_workflow_1jxy (both steps) and simulated_workflow_6vxx;
    9. solve3D_addon and cont_refine3D_1jxy;
    10. flex_pca_blobs and solve3D_pyramid_blobs. Record their results.

    Exit criteria: the build and the fast gate pass; every case and test is recorded with its spread where it ran twice; S1, S3 and M's start are kept.

    Phase 2, 2026-10-16: ref_assign without rescans (stopped at two multi-threaded checks)¶

    Status: implemented. The assignment is identical, shown by the tester and by one-thread runs on real data. Stopped because two acceptance checks on multi-threaded runs fail by small margins, for the maintainer to decide. Paths are relative to /home/elmlundho/agent_runs/ms_speed. "Before" is the Phase 1 build (scratch/keep/build_phase1). "After" is this phase's Release build, kept as scratch/keep/build_phase2.

    Files changed.

    • src/main/strategies/search/probabilistic/simple_eul_prob_tab.f90, ref_assign (the assignment of particles to references from the dense table of the prob refinement). The distance preparation and each reference's sort of the particles are unchanged. A reference's head is its closest particle not yet assigned.
    • The routine keeps a count of the unassigned particles instead of testing them all (any(ptcl_avail)) for every assignment.
    • For every particle it keeps the list of references whose head it is (head_first, ref_next). After an assignment it advances only that particle's list. The earlier code ran the head update on every reference, which changes only those heads.
    • State labels with several states. A particle's state is now the state of its closest reference over all states, computed per particle in parallel; an exact tie goes to the lowest reference index (written in the code).
      • The earlier global greedy frontier removed the closest available pair of reference and head particle first, and among equal distances the lowest reference index (minloc).
      • When a particle leaves that frontier, the pair's distance is the particle's minimum over all references. The chosen reference is the lowest index whose head is at that distance. The lowest-index reference at the particle's minimum has the particle or an equal distance as its head, so it is that reference.
      • The labels are therefore identical, ties included. The plan expected a difference in the tie case; there is none.
    • Within a state. A state's references are a contiguous block (the state's rank times the number of directions). Each of them keeps a head while a particle of the state is left, so the earlier gathering of the state's active references always returned the whole block, in order. The loop now runs over the block only, with the count and the lists.
    • The random draws (the calls of the likelihood sampler, their arguments and their order) are unchanged.
    • src/main/strategies/search/probabilistic/simple_eul_prob_tab_tester.f90: the test test_ref_assign_against_reference in the unit suite unit_pftc_align2D3D.
    • It keeps the earlier ref_assign as reference_assign, a copy of its algorithm working on the same distance array.
    • The tables have 150 particles: one state of 200 directions, three states of 200, and two states of one direction (each state's draw has a single reference).
    • The particles' states take turns, their angular distances are uniform over 0 to 20 degrees, and the distances are uniform over 0 to 5. The table's random values come from seed 20261016, and both assignments' draws from seed 20261017.
    • Every table holds the tie cases:
      • particle 1 is flat (every distance equal);
      • particle 2 ties its minimum between a reference of state 2 and one of state 3;
      • particle 3 between state 1 and state 3;
      • particle 4 has only invalid distances;
      • particles 5 and 6 are identical, which ties them in every reference's order.
    • The test asserts that:
      • every particle gets the same reference from both assignments;
      • the tie cases get the state of the lowest-index reference;
      • the reference assignment changes under another draw seed, so the agreement is not that of a draw-free assignment.
    • 24 checks pass.
    • doc/policies/3D/refine3D_policy.md, section 8: a subsection on the dense-table assignment.
