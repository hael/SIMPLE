    Accelerating refine=cont: fewer evaluations, a cheaper kernel, and a benchmark¶

    Implementation note, 2026-10-19, completed 2026-10-21. All seven stages are done: built, checked, and measured against the baseline. The measured gains are in section 2. The maintainer's rulings are in section 8. The findings come from a static review of master at 4da5cb9c0. The savings below are work counts read from the code. The rule of the local-workflow plan applies: do not infer a speedup percentage from removed calls (doc/refactoring_notes/planned/refine3d_local_workflow.md:264-267). Every stage is therefore measured with the benchmark of section 6.

    This is also a learning note for Maz. Each stage says why it comes where it does, what to run and what to look for, so the work can be followed and repeated without the conversation it came from.

    How to read this note:

    • Section 2 is the plan, as seven stages. Stage 2 ends with the baseline record, a table to fill in.
    • Sections 3 and 4 hold the findings the stages implement.
    • Sections 5 to 7 hold the measurement and test detail.

    Companion notes:

    • cont_kb_gather_performance.md: the fused gather and its list of future work.
    • doc/refactoring_notes/planned/refine3d_local_workflow.md: the workflow-level startup savings. This note covers the per-particle cost inside strategy3D_cont.
    • identical_speed_run*.md and single_state_speed_week*.md: the polar speed work this note compares against.

    The engine is shared, so every item also applies to the polish (pose_cont=yes) and to the proposed refine3D_local.

    1. The route and where it stands¶

    One particle runs one transaction:

    strategy3D_cont%srch_cont
  -> cartft_pose_opt%refine -> refine_pose -> refine_joint            (LM loop)
       -> cartft_calc%pose_normal_terms     objective, 5-gradient, 5x5 Gauss-Newton matrix
            -> gather_packed_bspline3_window_grad 27-sample B-spline gather and 3 derivatives, per pixel
  -> euclid_sigma2%calc_sigma2 -> cartft_calc%sigma_contribution     (euclid only)

    The search time of a particle is the number of full-disk passes it makes, times the cost of one pass. Section 3 reduces the first factor and section 4 the second.

    Done for this route so far:

    • Fused 3x3x3 KB gather. Median worker orientation-search time -36.8 to -37.5%, wall time -20.5 to -21.9%, on beta-gal (cont_kb_gather_performance.md:142-148).
    • Joint stage alone. 37% fewer LM iterations and 38% less transaction time than shift_then_joint (doc/refactoring_notes/completed/pose_cont_refactoring.md:1615-1618).
    • Dynamic scheduling of the matcher's particle loop. Commit aea5b1846, simple_strategy3D_matcher.f90:235.
    • A continuous gather (2026-10-20, after stage 5). The quadratic B-spline replaced the KB stencil in the gather (record after stage 5).

    None of the speed-week kernel changes reached src/main/cftc. The speed-run documents name refine=cont only as the identity case CR1. These polar items have a cont counterpart:

    Cost evidence. The only per-particle record is from beta-gal: 5,513 particles, box 256, nthr=12, an NCC objective, and the build before the fused gather. It shows 136,968 LM iterations, about 25 per particle, with a mean transaction time of 0.217 s and a maximum of 0.562 s (pose_cont_refactoring.md:1597-1604). Every LM iteration that evaluates makes one full-disk pass of the gather.

    2. Development stages¶

    The agent builds each stage, runs the checks it names and reports the results. The maintainer reviews and decides what is committed and pushed, and when. Stages are not gated on commits; several may go into one larger commit.

    What is measured (ruled 2026-10-20). The working tree, with every uncommitted change in it, is the code under development, so the builds and measurements use the full tree. That includes changes outside this work, such as PCG reconstruction work in progress. For an A/B pair the tree is snapshotted once (git diff HEAD, kept as ~/src/SIMPLE_cont_bench/patches/tree_snapshot_<time>.patch) and both variants are built from that one snapshot. A pair then differs only in the change being measured. The stage 2 baseline (builds A and B) predates this rule and stays the reference of the stage 2 and stage 3 records. The order is: measure first, then protect the kernel with tests, then make the changes that keep results identical, and only then the changes that alter them. Every gain can then be attributed to one stage.

    Stage 1: count the work¶

    Why. Today the bench record reports one number for the whole Cartesian search, match3D orientation search (simple_strategy3D_matcher.f90:373). A later change can speed the search up in two ways: fewer passes per particle (section 3), or cheaper passes (section 4). A single time cannot tell the two apart, and the policy forbids inferring a speedup from removed calls. The first change therefore makes the code report how much work it does.

    • What: the counters of section 5, added to the REFINE3D bench record. These include passes per particle, LM iterations, ns per pixel-evaluation and the actual/predicted ratio that diagnoses section 3.1.
    • Results: identical. Only BENCH content changes, and identity excludes BENCH files.
    • Check: the CR1 identity check (section 6.2), run in step 2.2.
    • Done when: one run reports these figures for each partition.

    Status (2026-10-19): done. It was committed in 0c9542e50 and checked in step 2.2: the CR1 identity holds, and the counters cost nothing measurable. The changes:

    • simple_cartft_calc.f90: each slot counts the pixels of its shells (get_ptcl_npix), and get_ref_bytes gives the bytes of the reference transforms.
    • simple_cartft_pose_opt.f90:
    • the solve counts its calculator evaluations (npasses);
    • each stage counts its evaluated trials (ntrials, beside nattempted, which includes the joint stage's bound rejections) and sums actual over predicted at accepted steps;
    • cartft_pose_work sums solves and writes the bench section.
    • simple_strategy3D_cont.f90: add_work adds the particle's solve, with its slot's pixel count and the sigma2 residual pass.
    • simple_strategy3D_matcher.f90:
    • one work record and the busy time per thread;
    • a THREAD-SECONDS block for every 3D search, following match2D;
    • the CONTINUOUS POSE WORK section for a Cartesian pass;
    • the reference bytes in the context;
    • the Cartesian reference read moved from startup to reference preparation.
    • refine3D_policy.md section 11.1 describes the new sections.

    Stage 2: benchmark workflow and baseline¶

    Why the baseline comes first. An optimization is only a claim until it has been compared with what came before: the same work, on the same machine, with the same build settings. The baseline is that "before". It is measured on the code as it is now, with the stage 1 counters in place and no optimization, and every later stage is judged against it.     2.4 Cover the realistic SNR range¶

    The range. Cryo-EM particles have an SNR of 0.02 or better. The default, snr=0.05, is a typical value. Step 2.5 also runs the polish regime at 0.02, the noisiest realistic case. The convergence problem of section 3.1 grows as the particle correlation falls, so this is where it is largest.

    A trap to avoid. Do not tune snr to reproduce a correlation measured with a different objective. The beta-gal record's 1 - NCC of 0.83 (correlation 0.17) was measured on sigma-whitened data, where the noisy high shells weigh as much as the low ones. Today's objfun=cc weights every pixel equally, so on the same data its correlation is much higher: 0.79 at snr=0.05 in the smoke runs below. Chasing 0.17 with the cc objective pushed snr to 0.0005, 40 times noisier than any real data set. That mistake was made, and corrected, while this note was written.

    The continuous gather (ruled 2026-10-20)¶

    Status (2026-10-20): done on the working tree (record below). Stage 5 found that the gather jumps where a sample's nearest grid point changes; the maintainer ruled to make it continuous.

    The cause. The gather takes three taps per axis around the nearest grid point, with KB weights normalized per axis. At a half-integer offset the stencil moves to the next cell: one tap at distance 1.5 leaves and another enters. The KB window is 1/3 at its edge, about 1% of its centre, so the leaving tap carries about 0.7% of the weight, and the value jumps by that much of the difference between the two outer coefficients. The derivative jumps too.

    The choice. A window whose value and slope vanish at 1.5 makes the value and the derivative carry across every switch, on the same three taps. Two such windows were compared in a one-dimensional model of the gather: the padf=2 transform of an object in the central half of the padded box, sampled off grid and compared with the exact transform of the tapered object, the taper being the stencil's own on-grid response, as get_ptcl_taper makes it.

    Window Value error Derivative error Jump at a switch
    KB (before) 4.1e-3 6.4e-2 1.1e-2
    KB less its edge value and slope 1.1e-2 1.4e-1 0
    Quadratic B-spline 3.2e-3 3.2e-2 0

    The quadratic B-spline fits the three taps exactly (support [-1.5, 1.5]), is continuous with its first derivative, and its weights sum to one at every offset, so the per-axis normalization goes. It is also more accurate than the KB stencil in this model, and its derivative twice as accurate. Its weights are three quadratics per axis instead of nine degree-14 polynomials.

    Keeping the polar link. The particle carries the stencil's taper (O5 of the pose_cont refactoring), and the polar and Cartesian representations share one sigma2 store, which the taper's noise-power factor scales. A B-spline taper on the particle would shift that factor by about 8% at a typical mask, which the sigma agreement tests (N14, N33) bound at 4-9%. So the particle keeps the KB taper, and the reference is weighted instead: set_ref multiplies the padded volume, per axis, by the KB stencil's response over the B-spline stencil's (ref_weight, 0.92 at the native box edge). On grid, the B-spline gather of the weighted transform equals the KB gather of the unweighted one exactly (circular convolution), so the model is the polar branch's there. The model puts this at the same accuracy against the KB-tapered target as the plain B-spline (3.1e-3, derivative 3.2e-2).

    3. Fewer passes per particle (the LM driver)¶

    3.1 The CC Gauss-Newton matrix lacks the correlation factor¶

    What the code computes. finalize_cc_normal_terms (simple_cartft_calc.f90:958-981) turns the sums into three things:

    • the objective f = 1 - <x^, n(theta)>, where x^ = x/|x| and n = m/|m| is the unit model;
    • its gradient -<x^, J_n>;
    • the matrix H_GN = J_n^T J_n, computed as hessian/prediction_power - mg mg^T/prediction_power**2.

    Why it is too large.

    1. The exact Hessian is -<x^, d2n>.
    2. Because |n| = 1, we have <n, d2n> = -|J_n|^2.
    3. Write x^ = c n + sqrt(1-c^2) u, where c is the correlation and u is the noise direction. The noise term averages to zero.
    4. So H ~ c J_n^T J_n, and H_GN is too large by a factor 1/c.

    Consequence. Each LM step is c times the Newton step. The pose error shrinks only by (1 - c) per iteration, and the objective gap by (1 - c)^2.

    The beta-gal record fits this.

    • At c ~ 0.17, with the 1e-6 relative stop of section 3.3, the contraction predicts about 18 accepted steps.
    • The run averaged about 25 LM iterations per particle, over a spread of correlations.
    • The pre-refactor refiner had the same finalize and the same LM constants: lines 684-706 and 43-47 of git show 214fad5d6^:src/main/volume/simple_cartesian_pose_refiner.f90.

    But that c is a whitened correlation. The old objective was a normalized correlation on sigma-whitened data, where the noisy high shells weigh as much as the low ones, so its correlation was low. Today's objfun=cc weights every pixel equally, and on the same data its correlation is far higher. In the smoke runs (stage 2) it is 0.65-0.78 at SNR 0.02-0.05, with about 10 LM iterations per solve, and the steps are only about 1.3 times too short. The fix is still right, but at realistic SNR its gain is modest. The large factor returns for any objective whose correlation is low, such as one on whitened data.

    Signature to look for with the counters of section 5. An undamped step predicts a reduction of (1/2) g^T H_GN^-1 g, and the true quadratic gives (1 - c/2) g^T H_GN^-1 g. Accepted steps should therefore show actual/predicted ~ 2 - c: almost no rejections, and most accepted steps in the 1.75-2.5 bin of the histogram for a correlation below 0.25.

    Change (stage 4). In finalize_cc_normal_terms, multiply the matrix by c = cross_real/normalizer, with a small positive floor. This is a one-line change. The optimum is unchanged, but the path changes, and with it the endpoints at tolerance level.

    As built (stage 4 record). The factor is not c itself but the regression slope of the normalized data on the normalized model, weighted by |f|^2; it equals c when every shell has the same slope. The weighting matters because the matrix takes its curvature from the high frequencies, and the correlation falls with frequency.

    objfun=euclid is different. It is the production objective of refine3D_auto and of the proposed refine3D_local.

    • L = sum |m - x|^2 / P, with H_GN = 2 J^T J / P. This is right on average when the reference amplitude matches the data.
    • If the reference is beta times the data signal, then H_GN/H ~ beta.
    • A filtered reference (beta < 1 at high k) therefore over-steps and pays in rejections and damping.

    Stage 2 measures the ratio and the rejection rate. A euclid change follows only if they show over-stepping.

    Stage 4 result. They do on beta-gal, and an unweighted slope does not help: it stays near 1, because the reference's overall amplitude matches the data's. The slope weighted by |f|^2, the same correction as cc's, halves the over-steps (stage 4 record, finding 1).

    3.3 The stopping rule is far below the noise¶

    Current rule. LM_ACCEPTED_RELATIVE_TOL = 1e-6 (simple_cartft_pose_opt.f90:38; the exit is at :563-564). A step ends the solve only when it reduces an objective near 0.83 by less than about 8e-7.

    For comparison:

    • The polar continuous in-plane solve stops at 1e-4 (JOINT_IMPROVE_REL_TOL, simple_pftc_shsrch_grad.f90:505).
    • check_cont_conv counts a particle as stable at 0.5 degrees and 1 A.

    Changes (stage 4):

    • Add a step tolerance in physical units: a small fraction of cont_conv_rot and cont_conv_shift.
    • Skip the evaluation of a trial whose predicted relative reduction is already below the tolerance. Such a trial would be accepted and would end the loop, so skipping it saves the last pass.

    Both change results. The tolerance values are set from the stage 4 profile, together with section 3.1, since a correct matrix makes fewer, larger steps.

    As built (stage 4 record). Only the second change, with the tolerance kept at 1e-6.     4. Cheaper passes (the kernel)¶

    4.1 Friedel symmetry¶

    pose_normal_terms loops over the full disk (simple_cartft_calc.f90:677-680). Every term is Hermitian between (h,k) and (-h,-k):

    • The observation is expand_ft of a real image (simple_matcher_2Dprep.f90:147-148), so X(-h,-k) = conj X(h,k).
    • The transfer |C|/sqrt(sigma2) is even.
    • The shift phase conjugates.
    • The gather is Hermitian: V(-loc) = conj V(loc) and dV(-loc) = -conj dV(loc). The rotation lever arm also changes sign, so the rotation Jacobians conjugate.

    So every summand takes the same value at the two Friedel mates: |r|^2, Re(J^H r), Re(J_a^H J_b) and the CC sums.

    Change (stage 6a). Loop over h > 0, plus the half line h = 0, k > 0, with weight 2. Visit the DC pixel once if the band includes shell 0. This halves the pixel work of every pass, including sigma_contribution (its per-shell sums double the same way) and shift_normal_terms.

    Details:

    • Rounding changes, because the gather of the mirrored stencil sums in reverse order.
    • The Nyquist pixels (+-box/2, 0) and (0, +-box/2) matter only when kto = box/2. Handle them explicitly.
    • The particle slots can then store the half plane, which halves their memory. transfer is real but stored as complex (:37); storing it real halves it again.

    4.2 The shift phase¶

    Current cost. Two double-precision transcendental calls per pixel (:688-689). The same code appears in shift_normal_terms, sigma_contribution and predict.

    Change (stage 6a). The phase separates as exp(2 pi i (h s1 + k s2)/box) = e_h(s1) e_k(s2). Build two 1-D tables per evaluation: 2(2 kto + 1) sin/cos pairs instead of about pi kto^2. Rounding changes.

    4.3 Normal-term arithmetic¶

    In :684-720, m = wp val is the model and wp = phase transfer. All of the following belong to stage 6a.

    Hessian entries. All 25 entries are accumulated (:703-708, :713-719), but only 15 are unique.

    Shift Jacobians. They are i f m (:699). It follows that:

    • the shift components of model_gradient are identically zero;
    • H(4:5,4:5) = sum f_a f_b |m|^2;
    • H(rotation a, shift) = -sum f Im(conj(J_a) m);
    • the shift gradient is -sum f Im(conj(m) x).

    f_h depends on h, and f_k is fixed along a row. These terms are therefore row sums that are multiplied by k at the row end.

    Rotation Jacobians. The three rotation Jacobians (:685-697) are the components of wp (dval x loc). One complex cross product replaces building dloc and three sum(cmplx(dval,dp)*dloc(:,axis)) calls.

    Objective branch. The select case(objfun) sits inside the pixel loop (:700). Either hoist it, or accumulate one set of sufficient statistics and finalize both objectives from it. The set is: sum |m|^2, sum Re conj(x) m, sum Re J^H m, sum Re J^H x and J^H J.

    Smaller items:

    • The CC branch recomputes sum |x|^2 on every evaluation (:710). For a CC slot, p%power already holds it (same shells, weight 1).
    • The per-pixel matmul(real([h,k,0],dp), rotmat) (:681) can be computed as h r1 + k r2, where r1 and r2 are the padded rotation rows formed once per evaluation. The gather note made keeping the matmul a non-goal of that change only.

    4.4 The gather¶

    The gather is simple_cartesian_fourier.f90:141-212.

    KB weights (stage 6b; superseded on 2026-10-20 by the continuous gather, whose B-spline weights are three quadratics per axis).

    • Per pixel there are three elemental calls of apod_fast_value_deriv on 3-vectors (:166). That is nine scalar degree-14 Horner evaluations, each with an error stop parameter check (simple_kbinterpol.f90:169-196).
    • The Release flags have no LTO (cmake/CompilerConfig.cmake:107). Calls that cross module boundaries are therefore not inlined; this covers both the KB calls and the per-pixel gather call.

    There are two options. Both must stay inside the 32-epsilon oracle contract of the gather note:

    • one 9-lane evaluation (12-lane padded) in the gather's own module;
    • a table of the three weights and derivatives per fractional offset, which needs three lookups per pixel.

    Scaling (stage 3a). padsc (= 8) multiplies the value and the three derivatives at every pixel (simple_cartft_calc.f90:915-916). Fold it into the reference when it is built. Because 8 is a power of two, the result is bit-identical, barring overflow.

    Indexing (stage 6a; ruled 2026-10-19: a branch-free gather; moved from stage 3 on 2026-10-20).

    • Today each sample costs three wrap-table lookups, the packed/Friedel branch and two conditional index adds (simple_cartesian_fourier.f90:183-211).
    • On the reference of section 4.5, each 3-tap run along x is three contiguous complex values at a fixed offset. There is no wrap, no Friedel branch and no conditional index.
    • Keeping today's accumulation order keeps the result bit-identical.
    • Vectorizing across the three taps reorders the sums, so it belongs to stage 6b.
    • Outcome (stage 6 record): the cube lost again on the half plane and was dropped; 6b contracts the taps one axis at a time on the packed layout.

    4.5 Loop bounds and the reference layout¶

    Loop bounds (stage 6a). The pixel loops visit the full (box+1)^2 square and test shells (:677-680). Bound them by kto, and by h >= 0 under section 4.1.

    Reference layout (stage 6a; ruled 2026-10-19; moved from stage 3 on 2026-10-20). The reference becomes a full (unpacked) complex cube. Measured alone in stage 3 it is slower at production bands. It doubles the working set of a full-disk pass, because the packed layout lets a pixel and its Friedel mate share memory (stage 3 record). So it is adopted only together with the half-plane, if the measurement there says so. On the half plane it was 18% slower on beta-gal (stage 6 record), so it was not adopted.

    • Extent. It is centred on the origin and covers the band of the reference file (kto, the header's band). Its half-side is padf kto + 2 voxels per axis. A pixel of shell at most kto has |loc| < padf (kto + 0.5), and the 3-tap stencil reaches one voxel beyond nint(loc), so the cube holds every sample a pass can need.
    • Construction. It is filled once from the padded transform, as copies for h >= 0 and exact conjugates for h < 0. It therefore holds exactly the values the packed gather fetches today.
    • Memory per state and half. (2(padf kto + 2) + 1)^3 complex values, against today's 0.54 GB at box_crop 256 (pose_cont_refactoring.md:325):
    • smaller below about 0.78 of Nyquist; at beta-gal's shell 87 of 128 it is 0.35 GB;
    • up to about twice today's size at Nyquist, 1.1 GB.

    The benchmark reports reference memory against this. The figures matter more under the autoscale=no default proposed for refine3D_local (refine3d_local_workflow.md:107). - Consequences: - predict, a test instrument that today covers shells up to box/2, stops at the reference's band. - check_eval_args refuses a slot band beyond the reference band. With that guarantee, the per-pixel inside test can go.

    Precision. Keep the single-precision gather and the double accumulation; the gather note rejects lower precision. Single-precision per-pixel products with double accumulation are possible, but they change LM decisions at the margin. They are not planned.

    5. Counters (stage 1)¶

    When l_cart_refine is set, the REFINE3D bench record gains a CONTINUOUS POSE WORK section, summed over the partition's solves. It reports:

    • solves by CARTFT_* status;
    • LM iterations, trial evaluations (evaluated trials, not nattempted), accepted steps and bound hits;
    • calculator passes (the solve's evaluations plus the sigma2 residual pass) and pixel-evaluations (passes times the pixels of the slot's shells in the full disk);
    • passes and LM iterations per solve;
    • the solves whose joint stage reached the iteration cap (they still end "accepted");
    • a histogram of actual/predicted at accepted steps, in the bins 0.25-0.75, 0.75-1.25, 1.25-1.75, 1.75-2.5 and >= 2.5. A histogram rather than a mean, because steps whose predicted reduction is near zero give ratios that ruin a mean. The bin around 2 - cc is the signature described in section 3.1;
    • the search thread-seconds per pixel-evaluation, in ns.

    Elsewhere in the record:

    • Thread-seconds. The search's thread-seconds sit in a THREAD-SECONDS block written for every 3D search, as match2D does. They are the busy time per particle, so the time per pixel-evaluation covers the whole particle search.
    • Reference memory. The context gives the bytes of all Cartesian reference transforms.
    • Reference read. The read, padding and transform of cart_refvols_*.bin move from "startup/setup" to "reference preparation".

    Implementation. Each thread keeps its own work record and busy time, and they are merged after the parallel loop. Nothing is written per particle. This mirrors the THREAD-SECONDS block and the evaluation counters of the prob-table records.

    The CR1 identity check is how the speed runs judged refine=cont (case CR1 of identical_speed_run.md). Run simple_test_exec test=cont_refine3D_1jxy nthr=1 with each build, each in an empty directory of its own. Then compare the metrics.tsv each leaves there: every check value must be equal.

    6.3 Performance (stage 2)¶

    The simulated benchmark, cont_refine3D_bench¶

    Form (ruled 2026-10-19). A simple_test_exec program outside the unit suite.

    • It is reachable as simple_test_exec test=cont_refine3D_bench, but it has no CTest entry, like rec3D_backends (test_environment_policy.md section 1.3).
    • It measures. It asserts nothing about time and holds no metric to a floor.

    What it does:

    1. The truth. It builds the embedded 1JYX model at box 256 and 0.73 A. This is E25's 187 A extent on a finer grid.
    2. The particles. It simulates nptcls particles (default 10 000) with E25's CTF spread, at snr (default 0.05, a typical particle SNR; real particles are 0.02 or better, step 2.4).
    3. The project and the reference. It writes a project with the truth CTF, the truth poses and the fields a discrete workflow leaves. The reference is reconstruct3D of that project, in reference/, with its own half-maps. This is the reference a converged refinement leaves, on the particles' amplitude scale.

    Why not the truth map: euclid's Gauss-Newton matrix is right only when the reference has the data's scale (section 3.1). The pdb2mrc map has an arbitrary scale next to noise-normalized particles. A first smoke run against it put 77% of euclid's accepted steps in the 1.75-2.5 bin, which was an artefact of the scale, not production behaviour. 4. The cases. For each regime it perturbs every truth pose by exactly the regime's error. It then runs one refine3D refine=cont pass per objective against that reference. The pass runs on the native grid (no box_crop) and the production joint route, with trs 6.5 A (E25's 5 pixels):

    Regime Pose error Band athres_cont Stands for
    polish 2 degrees, 1 A lp 3 A the default, 10 degrees the error a discrete search leaves, in a finishing band
    capture 15 degrees, 2.6 A lp 8 A 15 degrees E25
    1. The report. For every case, metrics.tsv gets:
    2. the seed's and the result's median rotation error (degrees) and median shift error (A);
    3. the fraction inside the basin width at the band;
    4. the mean corr_cart and the improved fraction;
    5. the settings.

    Recording the truth metrics with the timings means a faster arm that converges less cannot pass unnoticed.

    Keys:

    Key Effect

    objfun=euclid\|cc one objective (default: both)
    nptcls, snr the simulation
    nparts distributes each pass
    nthr threads
    seed_offset moves every seed (handled by the front door of simple_test_exec)

    Outputs. Everything goes into ./cont_refine3D_bench/, and the program refuses to start when that directory exists. It holds:

    • metrics.tsv;
    • the fixture;
    • one directory per case (polish_euclid, polish_cc, capture_euclid, capture_cc), each with its project and its BENCH/.

    Real data: the frozen beta-gal checkpoint¶

    The workload is 5,513 particles at box 256 with D2 symmetry, the run of pose_cont_refactoring.md (lines 1569-1576). Each run starts in a fresh copy of the checkpoint directory:

    simple_exec prg=refine3D mkdir=no vol1=recvol_state01.mrc mskdiam=180 pgrp=d2 objfun=euclid refine=cont maxits=1 nthr=12

    The comparison standard, the one the fused gather was held to (cont_kb_gather_performance.md:101-106):

    • three order-balanced pairs from fresh copies;
    • judged on the median worker orientation-search time;
    • memory within 5%, and matching work counts for the identical stages.

    6.4 Why the SNR must be realistic¶

    Iteration counts depend on the correlation (section 3.1).

    • E25 runs at SNR 1 (simple_strategy3D_cont_1jyx_tester.f90:50), far above the realistic 0.02-0.1.
    • The pose-optimizer and pose-strategy unit fixtures are noise-free observations from the calculator's own predict (simple_cartft_pose_opt_tester.f90:127).

    At a correlation near 1 the Gauss-Newton matrix is nearly exact. No existing cont test can therefore show the problem of section 3.1, and timings taken from them would understate the iteration count.
