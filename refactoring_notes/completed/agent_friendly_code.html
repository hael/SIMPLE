    Agent-friendly code¶

    Status, 2026-11-05: delivered with this note: section 2 and the defect fixes of section 5 (1-7). The run agent_friendly (section 8) carried out section 7 on the dell on 2026-11-05, uncommitted for the maintainer's review; its record is the Progress section below and its summary the report. Phase 6 (ruled after the report) adopted O1 and O4 and finished the in-bounds remainder. Left for the follow-up run agent_friendly2 on ms_posterior2's tree, since they change its files: R4/X4, C3, C4, the moves of 3.4 (R6), the judging runs of 3.7 and the phase-6 remainder listed in its Progress entry.

    1. Why¶

    A coding agent finds code by text search, reads files in slices, keeps nothing between sessions, and learns that it was wrong only from the compiler, a THROW_HARD or a test. Four properties decide how well it works in a codebase, and they help developers for the same reasons:

    1. Locality: what a change touches can be found by search and read in a few files.
    2. Explicit contracts: what a routine depends on, and what must happen before it, is visible at the call or enforced by the code.
    3. Loud failure: a mistake stops the build, the run or a test within seconds.
    4. One name per concept, one way to do a thing.

    SIMPLE already has much of this: no global singletons (params_glob and build_glob have no references), testers next to their code, a fast gate of about 30 s and unit suites of seconds, static consistency checks in the gate (test registry, !@descr, flex DAG), the short-comment and single-code-path rules, no backwards-compatibility shims, and domain folders that mostly do not import parameters or builder (none in ori, opt, interp, cftc). The items below address what remains. They are small steps that neither depend on nor block the domain-driven design proposal, whose value objects (its section 6) are the long-term answer to unit and key mistakes.

    2. Delivered with this note: folder guides that load themselves¶

    • The src/main folder guides (.github/skills/simple-main-*) lead with the folder's rules, silent ones first, then its call order, what it does not own, its couplings and its tests. New guides: cftc, flex, sieve, sigma2, and strategies split by subfolder; preprocess, image_processing and quality are folded into the guides of their owners. apis has no import (its guide is a map), and src/main only points to simple-main-root, since a guide there would load on every read below it.
    • A CLAUDE.md in the folder imports the guide, so Claude Code loads it the first time a file in that folder or below is read; src/CLAUDE.md and production/CLAUDE.md import simple-modern-fortran. Copilot reads the skills as before. Edit the SKILL.md, never the CLAUDE.md.
    • scripts/check_guide_imports.py runs in the fast gate: Claude Code drops a missing import without notice.
    • Basis: in the four sessions on record before this change (2026-11-02 and 03), nine subsystems with a guide were edited and none had its guide loaded before the first edit.

    3. Proposed items¶

    Ordered by payoff for the effort.

    3.1 Silent rules become checks¶

    Each rule a guide marks as silent is a place where neither an agent nor a developer gets feedback. Where a check is cheap, add it and cut the guide entry to the rule and the name of the check. Forms: a generation counter for call-order rules (the setter bumps it, the preparation records it, the user compares once per call, never in an inner loop); a stop instead of a default; a debug-build assertion where the check costs time. Each converted rule gets a tester that commits the violation and expects the stop.

    3.2 A static check of the command-line chain¶

    The params and ui audit found keys that fail without error, or fail at a user's first try. A static check over the source tree catches all of them, in the pattern of check_test_registry.py:

    • declared in parameters but never bound by the parser: mul (read by oriops and volops, so always 1.0) and import_type (always auto, so the destination checks of import_starproject never run);
    • UI inputs that are not accepted keys, so giving one stops the program: positive, heldout, rmsd_file, stk_traj;
    • the accepted-key generator (scripts/simple_args_generator.pl) reads past the type, because contains is not indented: cntfile, silent, final_planned and the fragment 1.0] are accepted keys;
    • private programs in neither the public UI nor simple_private_prgs.f90 get no required-key check, and that table's count is hard-coded;
    • a key bound twice: rec_states (simple_parameters_parse.f90).

    Proposal: scripts/check_cli_chain.py in the fast gate (every UI input is an accepted key, every accepted key is bound, every private program has a table entry) and a generator that stops at end type. Fixing today's violations needs the rulings of section 5.

    3.3 Orientation keys¶

    Particle parameters have fixed slots with named indices (I_* in simple_defs_ori). Any other key goes to a hash: get of a missing key returns 0.0 (simple_hash.f90, get) and set of a misspelt key adds a new one (simple_ori.f90, set_1). About 8,000 calls of the get/set family name their key as a string literal (630 distinct keys across orientations, command lines and reports); 671 guard with isthere. The particle slots class, eo, corr and others count as present only when non-zero. A scan of the 630 keys for pairs one edit apart found no live misspelling.

    Ruled (section 5, 12): a missing key keeps returning 0. What remains is the presence rule in the ori guide, the fixed get_neven (section 5, 7) and, optionally, a registry of known literal keys checked statically as in 3.2, which catches a misspelt key at the gate without changing get.

    3.4 One folder per owner¶

    Guides attach to folders, so a folder that mixes owners gets no guide or one loaded for unrelated work. src/main holds sixteen loose files: builder, cmdline, convergence, the final reconstruction, the refine3D stage plan, startup, states controller and workflow controller, external-reference pose initialization, the class-average work project and the simulator, with their testers. A guide in src/main would load on every read below it. Proposal: move them into named folders, for example core/ (builder, cmdline) and refine3D/ (the refine3D modules and the external-reference initialization), with the rest placed by owner decision. Cost: git mv, a CMake re-configure (src/CMakeLists.txt collects main/*.f90 recursively), guide and doc path updates; no aliases (release 4).

    3.5 Descriptive names for numbered specifics¶

    About 100 generic bindings dispatch to specifics numbered _1, _2 (mirror_ref_pft_1/_2, gen_corr_for_rot_8_1/_2). At a call site the body that runs depends on the argument types, and a search lands on the binding. Rename each specific by what distinguishes it (_by_index, _by_pft) and keep the generic name. Mechanical, one folder per change; the compiler checks it.

    3.6 A glossary¶

    One concept under several names costs more than abbreviations do. The even/odd half is iseven (200 uses), ieo (146) and the key 'eo' (98); state 0 means rejected; _8 marks double-precision variants and l_ logical flags; box/box_crop, smpd/smpd_crop, kfromto, trs, nspace, the ptcl2D/ptcl3D and cls2D/cls3D segments, sampled/updatecnt. Proposal: one page, doc/glossary.md, linked from simple-architecture and CLAUDE.md; new code uses its terms. It records today's code names and does not replace the domain language of the DDD proposal (its section 4).

    3.7 A judging run per workflow¶

    A change meant to improve results needs a run that can show it. simulated_workflow misses the map in 1 to 2 of 20 runs (profile of 2026-10-19), so one run shows breakage, not improvement. Proposal: for refine3D, solve2D, solve3D and the stream, one fixed-seed, fixed-data run of a few minutes with its metric, its noise band and how to read it, in doc/policies/test_environment_policy.md. test=profile and test=identity provide the machinery.

    3.8 A Fortran language server (experiment)¶

    Claude Code connects language servers through plugins (an .lsp.json naming the server and the extensions): diagnostics after each edit, and a read-only LSP tool for definitions and references by symbol, which plain search cannot do for the 254 bindings named new/kill/get/set/execute. There is no official Fortran plugin; the candidate is fortls (pip), not installed on the dell. Try it in user space with a local plugin for .f90 and measure: resolution of type-bound procedures into submodules, indexing time and memory on SIMPLE, and false diagnostics from THROW_* macros and generated sources. Drop it if it does not cope.

    4. Not proposed¶

    • Breaking up parameters (662 fields) or the (params, build) signature (134 routines). It hides what a routine reads, but it is the layering policy and a rewrite would not pay. New domain code stays on narrow inputs (the exception today: ten volume modules use parameters).
    • Splitting files by size (sixteen over 2,000 lines). An agent reads in slices; cohesion matters more than length.
    • Renaming idiomatic new/kill/get/set. The lifecycle symmetry is worth more than easier search; 3.8 addresses search.
