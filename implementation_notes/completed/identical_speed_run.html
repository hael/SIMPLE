    Identical speed changes: the Mac run speed_mac¶

    Implementation note, 2026-10-17. Carried out 2026-10-17 (progress below; report in identical_speed_run_report.md). The execution plan of the unattended run speed_mac on the maintainer's Mac, made while the Oracle Linux test machine runs test_truth. It carries out the parts of the speed week that leave every result byte-identical: item 3 of multistate_speed_run_completed.md (the table reads), days 3 and 4 of single_state_speed_week_completed.md, and the identical items of that plan's section "Multi-state". The design is in those two notes; this note holds what the code check of 2026-10-17 changed, the identity test, the phases and the progress.

    Rulings of 2026-10-17¶

    • The run is a headless Claude Code session on the Mac, in a worktree of master, launched by the maintainer.
    • Identical changes only. Every item must leave the outputs of the identity cases byte-identical. Changes that alter results (single-precision weights in the score kernels, a cap on refined references, the worker fold of day 5) are not in this run.
    • Identity now, timings later. The run proves identity. Wall-time gains are measured afterwards on the test machine (once test_truth is done) and on the maintainer's PfCRT and msp1 runs. The run may time single routines where an item's gain is in doubt (below).
    • The run may use most of the Mac (11 cores).

    What the code check of 2026-10-17 changed¶

    Five read-only checks of the code at 25d256886 (one per area) changed the plan in these places. Line numbers are approximate.

    Table reads (simple_eul_prob_tab.f90, simple_eul_prob_tab_neigh.f90, simple_commanders_prob.f90).

    • The master fills its dense table twice before it reads a part: once by allocate, because prob_candidate has default values (simple_eul_prob_tab_utils.f90, about line 20), and once in initialize_storage. Both passes sit inside the reported read time.
    • The initialisation cannot simply be dropped. The neighbourhood table uses the default values for the placeholder entry of a particle without candidates (read_tabs_to_glob, about line 1283), and the table tester sets only dist and relies on initialize_storage for the rest (tester, about lines 95-100 and 135-140). The dense table therefore needs its own entry type without default values, which the compact record (below) provides.
    • An OpenMP loop over the part files is safe: each part writes only its own particles' columns, and every buffer and unit is local. One exception: the read-modify-write of self%seed_nrots (about lines 932-933) races; collect the per-part values and check them after the loop.
    • The read does not check that every particle of the master appears in exactly one part. Today a missing particle keeps the initial values and an overlap lets the last part win silently. The parallel read adds that check.
    • In shared memory there is one part file, so the parallel read gains nothing there.
    • read_tabs_to_glob does open every part twice: the first pass reads the particle indices of every chunk to count the candidates per particle (about 4 of every 32 bytes), the second places the candidates. The order matters: the best evaluated reference is chosen with a strict <, and the assignment graph lists each reference's particles in file order. Reading every part into memory first would hold the candidates twice on the master, so the one-pass read is done only without that copy: the part writes its per-particle candidate counts after the particle indices, the first pass reads only those, and the second pass is unchanged. The gain is modest; if this is not simpler than today's code, the item is dropped and the reason recorded.

    The compact record for the dense table.

    • An unrefined entry is always (reference, in-plane index, distance, 0, 0, no shift). A refined entry replaces distance and in-plane index and sets the shift, only when the search returns irot > 0.
    • ref_assign reads only dist; assign_candidate reads all fields of the assigned entry; simple_strategy3D_prob.f90 reads only the assignment map. Nothing reads the shift of an unrefined entry.
    • So a row of (distance, in-plane index) per particle and reference, 8 bytes, plus a short list of (reference, shift) per particle for the refined ones, reproduces the same assignment and the same values handed on. File entries go from 28 to 8 bytes and the master's from 24 to 8.
    • The neighbourhood table shares the writer (begin_write, flush_candidate_buffers, write_tab) and the empty-part writer (write_empty_prob_tab). The dense table gets its own writer, reader and empty-part writer, with a format word in the header; the neighbourhood and 2D tables keep theirs.
    • Side gain: append_or_replace (utils, about line 113) scans a particle's entries backwards for every refined reference; with rows indexed by reference it is one store.

    The shift refinement (src/main/pftc/).

    • Every L-BFGS-B evaluation goes through gen_corr_grad_for_rot_8 (simple_polarft_corr.f90, about lines 881-900), which copies the reference to double precision; the kernel then rebuilds the shift matrix (gen_shmat4aln_8).
    • The "copied twice" path of the week plan is dead: gen_corr_grad_only_for_rot_8 is called only from grad_shsrch_gcostfun, which L-BFGS-B never reaches because the shift search sets the combined cost-and-gradient function. It is deleted. gcostfun_8 stays set, since simple_opt_lbfgsb.f90 checks that one gradient function is associated. shift_ref (simple_polarft_geom.f90) has no caller and is deleted.
    • The reference does not change during one minimisation, and the conversion to double precision is exact, so one copy per minimisation gives the same bits. The copy is about a tenth of one evaluation: 3-8% of the refinement. It goes into a dedicated per-thread buffer in the heap variables (simple_polarft_core.f90), loaded at the start of minimize; the kernels themselves stay as they are. pft_ref_8 cannot be reused (calc_frc and gen_sigma_contrib overwrite it), and a cache keyed on the reference index would serve stale data when references are replaced under the same index.
    • New: a repeated objective. After L-BFGS-B the alternation loop of grad_shsrch_minimize (simple_pftc_shsrch_grad.f90, about line 397) evaluates the objective over all rotations at the final shift. The L-BFGS-B callback evaluates the same objective at every accepted point (simple_opt_lbfgsb.f90, about lines 143-150), so when the minimiser ends on an accepted point the vector is recomputed bit for bit. It is not always so: in the multi-state table the start rotation comes from the particle-frame grid, not from a vector at the start shift, and if L-BFGS-B stops at its start point the loop can take a second pass. So: keep each all-rotation vector computed by gen_objfun_vals (before the loop, in the callback, in the loop) with its shift, and reuse it only when the shift is bitwise equal; the loop stays. This is worth more than the copy.
    • The shift-matrix range: gen_shmat4aln fills the double-precision matrix up to kfromto(2) and then converts it up to interpklim; the shells above kfromto(2) hold leftovers. Every consumer loops over kfromto only. Limit that one conversion to the searched shells; leave gen_shmat (used by shift_ptcl, all shells) alone.
    • New: allocations in the score loop. gen_likelihood_val_bank allocates scores(nrots) per reference (corr, about line 576) and sample_likelihood_dist allocates its cdf (utils, about line 490); the distance function is an internal procedure using host variables (corr, about lines 593-601), which gfortran may implement with a trampoline per call (-Wtrampolines tells). Per-thread buffers and a sampler working on an array of distances, evaluated in the same order, give the same results.
    • What must not change for identity: the order of the floating-point operations in the shift matrix (product, then sine and cosine of the first shell and of the step, then repeated multiplication) and in the kernels (the split of the angle loop, the running sums per shell, the weighted sum and the normalisation). Release builds use -O3 (with -mtune=generic on the Mac, -march=native on the test machine) and fuse multiply-adds, so any rewrite of those expressions can change bits.

    The nonuniform filter (src/main/nu_filt/, simple_nu_state_filter.f90).

    • Every candidate low-pass (up to 8) is filtered, written as an MRC pair, read back for the objective and read again for the composition. The write and read are lossless (float32, no rescaling), and nothing else reads the cache files.
    • The objective already runs one candidate at a time; the optimiser needs only the packed distance maps, which are held anyway. So the objective can run right after each candidate is filtered, with no volumes kept.
    • The composition already has a path that filters again from the input pair (compose_nu_labels_from_volume, simple_nu_filter_apply.f90, about lines 112-158): the same copy, taper, forward FFT, Butterworth multiply and inverse FFT, with plans made by FFTW_ESTIMATE, so the voxels are bit-identical. The input pair is killed just before the composition (simple_nu_state_filter.f90, about lines 137-147); moving the kills below it is enough. The composition's peak (about 6 volumes) stays below the setup's present peak (about 8).
    • postprocess_nu writes the caches and never composes; resolest composes from them with the input pair still alive. Both follow.
    • There are no timers inside the filter: the volume-assembly report has one line for all of it. The optimiser's tent smoothings (35 at 8 candidates) may cost more than the disk. Filtering again in the composition trades reads from the page cache for two inverse FFTs per candidate, which may not pay. Timers come first, and the composition change is kept only if a timing of the filter on a realistic pair says it is not slower.

    The states' volume assembly in parallel is not an identical change, and it leaves the run.

    • Several sums in a state's assembly depend on the thread count: the radial FSC (a double-precision reduction), the noise term of the ML regularisation, the smoothing weight of the filter's label update (a single-precision reduction that can flip near-tie labels), the phase randomisation (per-thread random streams), and FFTW plans made for the thread count. States run concurrently with fewer threads each would therefore differ from the serial loop, beyond rounding in the labels.
    • The filter is module state, its cache names carry no state index, and doc/policies/3D/separate_alignment_and_reconstruction_for_multistate_peak_mem_reduction.md forbids holding arrays of state volumes in assembly.
    • Instead, three identical items of the same code: per-state timers in the volume-assembly report; deleting two dead volume reads per state (restore_state_from_parts, simple_commanders_rec_distr.f90, about lines 111-112, and the stale comment at 44-45); and filling the filter's source halves from memory instead of reading back the files just written (about lines 460-479; copy the logical region only, since an image copy carries the FFT padding that a read leaves at zero).

    The reprojection model and the project reads (the distributed refine3D strategy).

    • materialize_reprojection_model (simple_refine3D_strategy.f90, about lines 525-553) builds a builder every iteration: a full project read, the toolboxes, the FSC read, the projection, and a write of the particle segment. The toolboxes are cheap except the symmetry distance table in neighbourhood mode; the project read is the cost.
    • Crop, directions and masks are fixed for one refine3D run (a stage that changes the crop starts a new one); the project changes every iteration. A persistent builder therefore keeps its toolboxes and refreshes its project every iteration, keeps the per-iteration set_projs check, and never holds a second full project between iterations. It is an allocatable component of the strategy, released in distr_cleanup (compile-time policy).
    • prob_align, volume assembly, the post-processing and commit_sigma2 run in the master process. Per distributed iteration the master reads the full project five times (the reprojection model, the strategy, prob_align, volume assembly's initialize_context, and commit_sigma2, which the week plan missed) and the particle segment twice (volume assembly's trailing reread, and refresh_matching_lp_from_project, which uses one record).
    • Two reads can go at once: volume assembly's trailing reread (nothing writes in between), and the one-record read (read_segment with fromto=[fromp,fromp]).
    • Handing the in-memory project to prob_align, volume assembly and commit_sigma2 needs a new entry, since commanders take only a command line; the PCG assembly from the master's (params, build) is the precedent. They must work on copies, not in place (the master never takes volume assembly's resolution fields, and writes the whole project at the end), and commit_sigma2's copy must reproduce what build_spproj sets for the project's cwd. Whether copying a 750,000-particle project is much faster than reading it is unmeasured; the run measures it first.

    The identity test¶

    An identical change is judged only by identity: the same case on the build before and the build after, at one thread with a fixed seed, outputs compared byte for byte. Multi-threaded runs are never used to judge an identical change; their draws vary from run to run (the run ms_speed stopped on such checks).

    The cases. All run with OMP_NUM_THREADS=1, in the environment of the CTest registration (production/CMakeLists.txt, simple_add_test: the build's bin/ and scripts/ first on PATH, SIMPLE_PATH the build, SIMPLE_QSYS=local, SIMPLE_EMAIL, GFORTRAN_UNBUFFERED_ALL=y). simple_test_exec fixes its own seed; the simple_exec cases set SIMPLE_SEED. The distributed master takes its thread count from OpenMP, not from nthr, so OMP_NUM_THREADS=1 is required.

    • project files (*.simple) record the date and time of every job (append_job_descr2jobproc), so they are compared through text dumps instead: simple_exec prg=print_project_field of ptcl2D, ptcl3D, cls2D, cls3D and out, written outside the case tree; the dumps are compared outputs;
    • solve3D_manifest.txt without its run identifier and digest lines;

    • Parallel code. At one thread an OpenMP loop runs serially, so the identity cases cannot show that parallel code is safe. Every loop this run parallelises (the reads of the part files) and every per-thread buffer it adds (the reference copy, the repeated objective, the score-loop buffers) gets a check in its tester that runs the routine at one and at four threads over many inputs and compares the results bit for bit.
    • When to run what. After every item: the item's build, the fast-gate suites, SW1, MSI, CCI, PCI and NU3D. At the end of every phase, in addition: SW6, the full Debug gate, and AD1 and CR1.     Common rules¶

    • Builds. Release builds out of tree for the identity cases, each in its own directory with its own install (the install prefix defaults to the build directory), configured as ~/src/SIMPLE/build/CMakeCache.txt (gfortran 16 from Homebrew, Release, BUILD_TESTS=ON, OpenMP, USE_ARCHOPT=ON). The base build is kept for the whole run. The Debug build lives in the worktree's build/: ./compile_debug.sh (a clean build with the fast gate, whose 60-second budget only holds on an idle machine) runs once in Phase 0 and at each phase's end with nothing else running; per item the Debug build is incremental (cmake --build build) and the fast-gate suites run with ctest -L "fast|provisional" in build/, passing when no entry fails.
    • Gates per item: the fast-gate suites pass on the incremental Debug build; python3 scripts/check_test_registry.py . passes whenever a tester changes; the identity cases are identical to the base.
    • No new tests or registrations. New checks go into the existing tester modules (the 3D table tester, the in-plane tester, the filter's tester), so the test registry and the files the run test_truth edits stay untouched. Those files are: production/CMakeLists.txt, production/simple_test_exec.f90, everything under src/main/commanders/test/ and src/main/ui/simple_test/, simple_parameters.f90, simple_parameters_parse.f90, simple_commanders_sim.f90, simple_ui_sim.f90, simple_test_utils.f90, simple_forked_process.f90, simple_forked_process_tester.f90, simple_parameters_phases.f90, src/main/exec/simple_test_exec_highlevel.f90, src/main/apis/simple_test_exec_api.f90, scripts/simple_args_generator.pl, scripts/check_test_registry.py, src/main/flex/run/simple_flex_pca_application_tester.f90, doc/policies/test_environment_policy.md, doc/user_guide/simulate_particles.md and test_suite_truth_and_robustness.md. A fix that needs one of them is recorded instead, for the maintainer. test_truth may also repair production code this run edits (the state handling of ref_assign, an empty state in the distributed PCG): ref_assign's algorithm stays as it is apart from how it reads the distances, and the report lists every file both runs touched.
    • Fix as you go. A defect found on the way is fixed in the phase that finds it, as an item of its own with its own diff. If the fix changes results, SW1 must pass its truth checks, CR1 its checks, and MSI must run to the end with every state populated; SW6 is reported but does not decide (its 80 picked particles make it pass on only some seeds). Then the base outputs are made again from a build with the fix, so the following items are still judged by identity. A design question is written up for the maintainer and the run goes on.
    • An item that cannot be made identical. Find the cause. If it is the item's own mistake, fix it. If the item cannot be identical (for example the compiler vectorises a rewritten loop differently), restore its files from the previous snapshot with a plain copy (no hard links, no preserved times) and touch them, so that make rebuilds them; record the cause with the evidence, and go on with the next item. Never widen the comparison, never add an exclusion, never rerun until a case passes.
    • One diff per item. After each item the source directories of the worktree (src, doc, scripts, production) are snapshotted with hard links (rsync -a --link-dest), and the item's diff is the difference between consecutive snapshots; the cumulative diff against HEAD is written too.
    • Nothing is committed; the maintainer reviews the diffs.
    • CPU, memory, disk. At most nine single-thread jobs at a time, the long ones started first (the Mac's cores are partly efficiency cores); builds take the cores left; the timings of items 11 and 14 run alone. The jobs' peak memories (measured in Phase 0 with /usr/bin/time -l) add up to at most 70% of the Mac's memory. An after-run whose outputs match is deleted once its dumps and logs are kept; the base outputs stay.
    • Not in this run. Results-changing items; the worker fold; the parallel state assembly; the generated indexes under doc/code_overview/; skill files (proposed text goes into the report).

    Phase 2, 2026-10-17: the polar kernels¶

    All four items are kept; each is byte-identical to the base on SW1, MSI, CCI, PCI and NU3D (each item built from its own snapshot), and SW6 is identical after the phase.

    • The shift-matrix conversion. gen_shmat4aln converts only the searched shells to single precision; all its consumers loop over kfromto.
    • The repeated objective. The shift search keeps the last all-rotation objective it computed inside minimize, with its shift, and reuses it when the shift is bitwise equal: the L-BFGS-B callback scores every accepted point, and the alternation loop then scores the point the minimiser ended on. Outside minimize nothing is cached, since the references may change between calls.
    • One reference copy per minimisation. A per-thread double-precision buffer (pft_ref_aln_8) is loaded at the start of minimize; gen_corr_for_rot_8_aln and gen_corr_grad_for_rot_8_aln call the unchanged kernels with it. The coarse searches, now private, use it too. gen_corr_grad_only_for_rot_8 (unreachable) and shift_ref (no caller) are deleted.
    • The score loop. The compiler confirmed both suspicions: heap trampolines for the internal distance functions (__gcc_nested_func_ptr_created per call; -Wtrampolines does not report heap trampolines) and a malloc of the score vector per call in gen_likelihood_val_bank. The likelihood routes now fill per-thread buffers and call sample_likelihood_dists, which shares its draw with sample_likelihood_dist (unchanged, still used by ref_assign). Two trampolines remain, in the bounded and power samplers used by the 2D sampling strategies and greedy_sub; they are outside the table fill and are left for a later change.
    • Tests (in-plane tester and 3D table tester, all exact): the scores do not depend on the shells above the searched band; the loaded reference evaluates as the copied one, with other evaluations in between; the shift searches (24 references, three starts, both objectives) and the likelihood scores (shifted and bank routes) at one and at four threads; the array sampler draws as the function sampler on 200 random sets.
    • Indication only (MSI, one thread, base run beside more jobs): the dense table's score loop 4.30 s before, 2.23 s after; its refinement 0.30 s and 0.19 s.
