## Request and context

Hans requested implementation validation before production policy. The existing research code supplies a local five-parameter analytic Jacobian and Levenberg--Marquardt (LM) solve in a Cartesian Fourier-plane workspace. It has passed componentwise finite differences and extensive matched-model capture experiments, but the complete weighted objective, normal equations, LM proposal, and independent forward model have not yet been verified by structurally separate oracles.

Hans also clarified the ownership boundary: particle-pose refinement must not be implemented as a callable feature of `reconstructor_pcg`. It requires its own particle-pose numerical module. Operations proven to be independent of reconstruction state may move to a neutral shared module used by both reconstruction and pose refinement.

The feature must not be called PCG pose polishing. PCG is a reconstruction solver whose unknown is the 3-D volume. The five-parameter LM unknown is one particle pose.

## Problem statement

Current tests strongly support the local interpolation and pose derivatives, but substantial implementation risk remains in the fused shell weighting, CTF application, $J^H J$, $J^H r$, damping/scaling, dense five-by-five solve, rollback, shared forward-model assumptions, and numerical ownership. Production integration would be premature until these contracts are independently verified and particle-pose code no longer depends on a volume-reconstruction object.

## Initial state

- `reconstructor_pcg` currently contains the Cartesian Fourier-plane, CTF/sigma, pose-normal-term, and bounded LM routines used by the research tests. This is a provisional location, not the accepted owner of particle-pose refinement.
- Focused tests cover fast Kaiser--Bessel derivatives, normalized stencils, shift and rotation derivatives, exact-pose stationarity, capture range, route dependence, bounds, and terminal states.
- The observations in the principal capture experiment were generated by the same forward evaluator used by the optimizer.
- No normal `refine3D` workflow calls the five-parameter LM.
- Ordinary SIMPLE behavior is unchanged unless separate future integration work is approved.

## Desired outcome

Separate particle-pose numerics from the PCG volume solver, then produce independent numerical evidence that the Cartesian five-parameter evaluator and LM driver implement their declared mathematical model correctly over representative CTF, shell-variance, volume, box, and frequency configurations.

## Required final endpoint

The validation slice is complete only when:

1. independent oracles reproduce the weighted objective, gradient, Gauss--Newton matrix, and one damped LM proposal within tolerances frozen after a separate numerical-calibration step and before the formal acceptance matrix;
2. valid CTF/sigma configurations remain finite and invalid variance inputs fail explicitly;
3. an oracle hierarchy comprising analytic Fourier objects, a tiny-box brute-force DFT, a slow reference Cartesian interpolator, and a finite-box projection path satisfies its separately declared comparison contracts;
4. rejection restores the complete input pose;
5. multiple boxes, Fourier ranges, and asymmetric volumes satisfy the same contract;
6. the particle-pose module does not depend on `reconstructor_pcg`, and any shared numerical module contains only operations demonstrated to be independent of reconstruction and particle state;
7. ordinary PCG reconstruction and the focused pose cases pass their regression gates on Oracle Linux; and
8. no UI, production caller, persistence, distributed workflow, or automatic activation is added.

Passing this endpoint permits drafting a separate SPEC for a standalone continuous `refine3D` validation mode. That future mode will follow the logical integration position of `inpl_cont` and offer the legacy `inpl_cont` route and the new five-parameter polisher as mutually exclusive user choices. This SPEC does not authorize either that caller or normal refinement integration.

## Scientific contract

### Pose coordinates

For an input pose $(R_0,t_0)$,

$$
q=(\omega_x,\omega_y,\omega_z,t_x,t_y),
\qquad
R=R_0\exp([\omega]_\times).
$$

Rotations are right tangent-space increments in radians. Shifts are image-plane pixels.

### Objective

The numerical fixture uses a shell-variance-weighted Cartesian Fourier-plane residual:

$$
\Phi(q)=\frac12\sum_{\mathbf{k}\in\Omega}
\frac{|M(q;\mathbf{k})-Y(\mathbf{k})|^2}{\sigma^2_{s(\mathbf{k})}}.
$$

$M$ must use the declared particle-specific CTF, Fourier shift phase, interpolation, normalization, and shell range. Reusing `build_transfer` and `whiten_observation` is permitted; their operation order and conventions must be tested rather than assumed.

The objective is not the existing PFTC matcher objective. Because the implemented test remains Cartesian, it does not require a polar-coordinate Jacobian/radial scaling factor. A future PFTC objective would require a separate derivation and SPEC.

### Local derivatives

The five residual-Jacobian columns must differentiate the executed fast Kaiser--Bessel polynomial and normalized stencil inside one fixed interpolation cell. Stencil crossings are a documented non-differentiable boundary and must be measured separately rather than forced through a derivative gate.

### LM step

The implemented step has the form

$$
(J^H J+\mu D)\delta=-J^H r.
$$

The independent oracle must verify the unscaled and scaled terms, damping diagonal, proposed step, predicted reduction, recomputed objective, acceptance decision, and complete rollback after rejection.

### Numerical ownership

- A particle-pose module owns the five-parameter objective, normal terms, LM state, bounds, acceptance, terminal outcomes, and pose rollback.
- `reconstructor_pcg` continues to own the PCG volume solve and reconstruction-specific workspace and policy.
- A neutral shared module may own only lower-level operations that are demonstrably independent of whether the caller is reconstructing a volume or refining a particle pose.
- Both reconstruction and particle-pose modules may depend on the neutral shared module. The particle-pose module must not depend on `reconstructor_pcg`.
- Shared extraction must preserve the executed numerical conventions and ordinary reconstruction behavior; superficial code similarity alone is not sufficient reason to share an operation.

### Forward-oracle hierarchy

Independence must come from different computational paths, not merely different source files:

1. **Production path:** Fourier volume to the executed fast Kaiser--Bessel interpolation path.
2. **Reference Cartesian interpolation:** Fourier volume to a deliberately simple, slow interpolation implementation that does not call the production gather or stencil helper.
3. **Brute-force DFT:** a tiny real-space volume, limited to a declared test-only box such as $8^3$ or $16^3$, evaluated directly at the rotated continuous Fourier coordinates without an FFT, Fourier-grid plane extraction, or Kaiser--Bessel interpolation.
4. **Finite-box projection:** real-space volume to a projected image and then an FFT, retaining its own cropping, padding, and boundary effects.

The direct oracle must declare five independent conventions. None may be inferred from another:

- **Origin:** for an even native box of length $N$, the zero-based real-space coordinate is $x_j=j-N/2$, so the spatial origin is zero-based voxel $j=N/2$ or one-based Fortran voxel $i=N/2+1$.
- **Frequency units:** $(h,k)$ are integer native-FFT indices and the corresponding continuous frequency is measured in cycles per voxel, so the exponent contains $1/N$.
- **Transform sign:** the forward transform uses the negative exponential.
- **Amplitude normalization:** an explicit factor $c_{\mathrm{FFT}}$ records the executed forward-FFT and padding convention; centering does not determine this factor.
- **Rotation convention:** `forward_plane` uses the row-vector frequency $[h,k,0]R$. Rotation-column tests must chain the direct-DFT spatial-frequency gradient through this exact convention and the declared right-tangent update $R=R_0\exp([\omega]_\times)$.

The origin convention is therefore

$$
x_j=j-\frac{N}{2},\qquad j=0,\ldots,N-1.
$$

Thus zero-based voxel $j=0$ is $x=-N/2$, while $j=N/2$ is the spatial origin $x=0$. `image%fft` moves that origin to FFT storage index 1 before the transform. This fixes the phase/origin convention, not the amplitude normalization.

Before specializing to SIMPLE, write the direct transform as

$$
F(\boldsymbol{\xi})=c_{\mathrm{FFT}}\sum_{\mathbf{x}}v(\mathbf{x})
\exp\left(-2\pi i\boldsymbol{\xi}\cdot\mathbf{x}\right).
$$

The executed native three-dimensional `image%fft` divides by the number of voxels, so $c_{\mathrm{FFT}}=1/N^3$ for a cubic native box. For a padded box of length $N_{\mathrm{pd}}=\mathrm{padf}\,N$, the FFT initially supplies $1/N_{\mathrm{pd}}^3$; `forward_plane` multiplies the gathered value by $\mathrm{padf}^3$, giving the same effective native factor

$$
\frac{\mathrm{padf}^3}{N_{\mathrm{pd}}^3}=\frac{1}{N^3}.
$$

This source-derived scaling contract is independent of the centering argument and must be tested independently with analytic-amplitude fixtures.

Define the rotated continuous frequency as

$$
\boldsymbol{\xi}_R(h,k)=\frac{1}{N}[h,k,0]R.
$$

Before shift and CTF, the corresponding source-specialized direct-DFT target is

$$
G_R(h,k)=\frac{1}{N^3}\sum_{\mathbf{x}}v(\mathbf{x})
\exp\left(-\frac{2\pi i}{N}
\left([h,k,0]R\right)\cdot\mathbf{x}\right).
$$

The brute-force transform must retain this origin, frequency, rotation, sign, and native-scale convention. Shift phase and CTF are applied as separately testable operations after the unshifted direct sum.

The same normalized direct sum supplies a non-interpolating spatial-frequency derivative,

$$
\nabla_{\boldsymbol{\xi}}F(\boldsymbol{\xi})
=-\frac{2\pi i}{N^3}\sum_{\mathbf{x}}\mathbf{x}v(\mathbf{x})
\exp\left(-2\pi i\boldsymbol{\xi}\cdot\mathbf{x}\right),
$$

which must be chained through the declared right-tangent rotation convention to test the three rotation columns independently of Kaiser--Bessel differentiation. Shift-phase derivatives are tested separately under the declared phase sign and frequency units.

Analytic fixtures must include centered and off-center deltas and a two-point configuration. For a voxel of amplitude $a$ at $\mathbf{x}_0$, the normalized Fourier value is

$$
F(\boldsymbol{\xi})=c_{\mathrm{FFT}}a
\exp\left(-2\pi i\boldsymbol{\xi}\cdot\mathbf{x}_0\right).
$$

For a unit-valued voxel under SIMPLE's native three-dimensional convention, the magnitude is therefore $1/N^3$, not one. An unscaled analytic sum may still be used for phase-only checks, but a production-path amplitude comparison must apply the declared $c_{\mathrm{FFT}}$. Gaussian and spherical fixtures may test radial amplitude and normalization, but their continuous closed forms must not be treated as exact transforms of sampled, truncated voxel arrays. A symmetric sphere cannot validate rotational identifiability. The two-point case tests phase superposition but remains rotationally degenerate about its connecting axis; a three-or-more-point non-collinear unequal-amplitude fixture or an asymmetric Gaussian mixture is required for the five rotational/shift derivative columns.

The existing Gaussian-mixture fixture places its nominal geometric center at $N/2+0.5$ in one-based array coordinates, half a voxel from SIMPLE's FFT origin at $N/2+1$. It remains a useful asymmetric robustness fixture, but it must not be treated as a zero-phase centered analytic object.

The four paths do not share one universal numerical tolerance. Analytic identities test signs, origins, and scaling; brute-force DFT versus production measures the complete grid/interpolation approximation; reference interpolation versus production isolates interpolation implementation; and finite-box projection measures a distinct discrete imaging path. Each comparison must be named and gated separately.

## Scope

- Independent weighted-objective oracle.
- Independent $J^H r$ and $J^H J$ oracle.
- Independent dense five-by-five damped solve.
- Ownership audit and extraction of the five-parameter particle objective and LM driver from `reconstructor_pcg` into a dedicated numerical module.
- Extraction of proven volume-independent overlap into a neutral shared module when that avoids duplication.
- CTF and shell-variance validation matrix.
- Analytic Fourier fixtures, a tiny-box brute-force DFT oracle, a structurally separate Cartesian interpolation oracle, and a separately named finite-box projection oracle.
- Multiple volume, box, and Fourier-range configurations.
- Focused Fortran tests, evidence telemetry, and Oracle Linux validation.
- Documentation and naming that distinguish LM pose refinement from PCG reconstruction.

## Out of scope

- `refine3D` UI, commander, strategy, metadata, restart, or distributed integration.
- Replacement or modification of `inpl_cont`; the mutually exclusive legacy/new route belongs to the later standalone-mode SPEC.
- PFTC pose derivatives or a PFTC five-parameter objective.
- A normal production acceptance, rollback, frequency, pose-prior, or reference-refresh policy.
- Behavioral changes to ordinary PCG or conventional reconstruction.
- Claims of FSC, real-data, or workflow benefit.
- Selection of direct joint, shift-first, or another production optimization sequence.

## Acceptance criteria

1. The fused objective agrees with an independent accumulation for constant and nonconstant positive shell-variance profiles under the absolute/relative tolerance frozen after calibration and before the acceptance cases run.
2. Independent residual Jacobian columns, $J^H r$, and $J^H J$ agree componentwise with the implementation under the same frozen tolerance policy.
3. One accepted and one rejected damped LM proposal agree with an independent dense five-by-five reference solve and acceptance calculation.
4. Rejected, invalid, singular, bounded-out, and finite-no-improvement trials preserve the complete input rotation and shift exactly within the declared representation tolerance.
5. Constant variance, smoothly varying variance, strongly varying finite positive variance, attenuated CTF shells, and CTF zeros remain finite and agree with their oracles.
6. Zero, negative, non-finite, or structurally invalid variance inputs fail through the declared numerical contract.
7. The four forward paths satisfy their separately frozen contracts: analytic identities establish coordinate/sign/scale conventions; the brute-force DFT measures complete interpolation error; the slow Cartesian interpolator isolates production interpolation; and the finite-box path is reported as a distinct operator. Stencil-switch cases are reported separately.
8. At least two box sizes, two Fourier ranges, and three deterministic asymmetric volumes pass without post-result tolerance changes.
9. Existing componentwise derivative, capture, pose-recovery, and default-path regression cases remain unchanged or pass with explicitly reviewed updates.
10. The focused validation cases and complete mother suite compile and pass on Oracle Linux with retained logs.
11. The source contains no production activation or new user-visible option for this numerical-validation slice.
12. Source inspection confirms that particle-pose tests call the dedicated pose module, the pose module does not import `reconstructor_pcg`, and any shared module exposes no PCG solver state or particle-policy state.
13. Focused reconstruction regression evidence shows that moving shared operations did not change ordinary PCG results within its existing contract.

## Constraints

- Preserve `doc/implementation_notes/continuous_3D_refinement_on_pcg_operator.md` as the frozen original proposal.
- Keep source inspection, compilation, runtime evidence, and scientific validation separate.
- Keep calibration fixtures distinct from formal acceptance fixtures. Freeze the absolute/relative tolerance policy before the acceptance matrix runs, and do not weaken it after observing acceptance failures.
- Use the exact executed polynomial/interpolation path for the implementation under test.
- Keep the independent forward oracle structurally separate enough to avoid an inverse crime.
- Enforce the brute-force DFT box limit in test code so the oracle cannot be used accidentally for production-sized volumes.
- Do not duplicate an operation merely to avoid a dependency; move genuinely common, state-independent numerics behind a neutral interface and keep owner-specific policy in its owner.
- Oracle Linux supplies authoritative compilation and runtime evidence; agents do not compile unless explicitly requested.

## Known challenges

- **CHALLENGE:** the current numerical API lives in `simple_reconstructor_pcg.f90`; separating particle-owned, reconstruction-owned, and genuinely shared calculations must preserve exact conventions without carrying PCG state into the particle module.
- **CHALLENGE:** single precision, FFT normalization, interpolation, and accumulated complex sums require tolerances based on a documented error model rather than arbitrary decimal equality.
- **CHALLENGE:** direct DFT, Fourier-grid interpolation, and a simulator with projection, cropping, padding, and FFT are different discrete operators; their expected discrepancies and normalization must be declared rather than hidden behind one tolerance.
- **CHALLENGE:** interpolation-stencil switches prevent a global differentiability claim.
- **CHALLENGE:** objective reduction and matched-model recovery do not prove production pose accuracy.

## Blockers before FINAL

1. **BLOCKER:** approve the calibration protocol, comparison metrics, safety-factor rule, and freeze point for objective, normal-term, and dense-step tolerances before implementation begins.
2. **BLOCKER:** confirm shift-phase convention, CTF order, and distinct comparison contracts for the analytic, brute-force DFT, reference-interpolation, and finite-box paths. The real-space origin, frequency units, transform sign, row-vector rotation convention, and native $1/N^3$ scale are now independently fixed from the executed SIMPLE source; the scale is not inferred from centering.
3. **BLOCKER:** complete and approve a routine-by-routine ownership map that identifies the dedicated particle module, reconstruction-only routines, and any neutral shared interface before moving code.

The integration boundary is resolved: this SPEC ends at numerical validation. A later SPEC will define a standalone `refine3D` mode in which `inpl_cont` and the five-parameter polisher are mutually exclusive alternatives.

## Assumptions

- **ASSUMPTION:** the current right-increment rotation convention and positive Fourier shift convention are the intended Cartesian pose conventions.
- **ASSUMPTION:** the current `build_transfer` and `whiten_observation` CTF/sigma semantics are the intended conventions for this validation slice.
- **ASSUMPTION:** a structurally separate slow oracle can be implemented with acceptable test-only cost.

## Open questions

2. What separately frozen error contract should govern direct DFT versus fast interpolation, reference interpolation versus fast interpolation, and finite-box projection versus the other discrete models?
3. Which current Fourier workspace, interpolation, CTF, sigma, and normalization operations are truly independent of both the PCG volume solve and particle-pose policy, and therefore belong in the neutral shared module?
