    A test suite that knows the truth: correctness, robustness and multi-state¶

    Implementation note, 2026-10-16. Phases 0 to 9 done (see Progress; the run test_truth carried out Phases 0 to 6, test_truth_sync Phases 7 to 9 on the merged code), the report file has not been written yet; the dataset layer follows. Written after the run ms_speed, which could not tell whether its multi-state schedule change was correct: no test knows the state labels, and the checks it used on beta-galactosidase measured run-to-run scatter, not correctness. The maintainer's points: multi-state results must be validated against known state labels, so on simulated data only; every high-level test must be shown to test what it claims; and robustness testing must be separated from correctness testing. A weekend on the Oracle Linux test machine is available, and a suite that is both robust and fast is the goal.

    Rulings of 2026-10-16¶

    • Heterogeneity models as proposed. Compositional beta-galactosidase states (chains removed) for the correctness tier, a conformational state (a rigid chain rotation) for the hard profile, blob phantoms for fast logic tests.
    • simulate_particles learns several volumes and populations. It no longer forces state 1; the mixture is made by the production program, not by a test-side workaround (section "The simulator").
    • Repair what can be repaired: the two failing multi-state tests and the weaknesses the audit finds, each with the profile that justifies the change.
    • Threads in correctness gates: the CTest thread count, with floors calibrated across seeds and thread settings (proposed, not objected to).
    • No outside driver.
    • Every high-level test is a SIMPLE commander, so the runner is one too: simple_test_exec test=nightly runs the whole suite.
    • A robustness profile is a commander that executes a test commander under command lines it generates itself (seed offsets, thread counts).

    • Nothing that runs, profiles or compares tests is a Python script. The existing registry lint (scripts/check_test_registry.py) stays a lint.

    • A review of this plan (2026-10-16) found eight design faults, all corrected below:

    • one state mapping for labels, maps and poses;
    • a discrimination metric with a duplicated-map control;
    • declared point groups and one frame and hand per state;
    • explicit fixture modes;
    • null distributions for unequal populations;
    • CPU reservations instead of thread counts;
    • a dispatcher with a failure and deadline contract;
    • paired production variants for the schedule comparison.

    The plain learning¶

    The policy (doc/policies/test_environment_policy.md, sections 2 and 6) already asks for the right things: truth instead of completion, floors with a stated origin, a negative control where cheap, reproducible draws. The suite does not yet live up to it in four ways:

    1. Multi-state has no working truth test.
    2. Two tests involve several states, flex_pca_blobs and solve3D_pyramid_blobs, and both fail on the current code before the state-separating stages.
    3. No test runs multi-state solve3D, multi-state refine3D or refine3D_states against known labels.
    4. The state metrics that exist use many-to-one majority recoding, which also passes identical maps, rather than a one-to-one matching.
    5. Correctness and robustness are confounded.
    6. Multi-threaded runs are not reproducible, so a single run's metric is a draw from a distribution.
    7. Floors were set from one or two runs, and several sit inside that distribution:
      • solve3D_addon: the 5° pose floor against values of 1.5-6°;
      • simulated_workflow_6vxx: about 80 particles, 6 of 8 seeds pass;
      • simulated_workflow_1jxy: a correlation floor of 0.80 against recorded values of 0.80-0.90.
    8. So a failure does not say whether the code is wrong or the draw was unlucky. That is the stop pattern of the last two runs.
    9. Claims are not checked against what runs.
    10. Each claim was found unexercised or unchecked:
      • flex_pca_blobs claims the class-average state refinement, but its refine3D_states_cavgs stops before the neighbourhood stage, so the 2,500-direction cap of refine3D_states was never run by any test;
      • simulated_workflow claims orientations are compared, and only the map is;
      • mini_stream claims picking and 2D, and checks a particle count and internal consistency.
    11. No test asserts that the path it claims actually ran.
    12. Some gates cannot fail, or cannot fail for the right reason.
    13. Map floors of 40 Å against 4-6 Å results.
    14. Pose checks only relative to another run, with no absolute floor.
    15. A pyramid purity floor of 0.45, barely above what random labels reach.
    16. A docking correlation that turns a non-finite value into 1.

    Four kinds of test, kept apart¶

    kind question how it is run how it passes
    identity did a refactoring change any result? one thread, fixed seed, the same case on two builds declared outputs byte-identical (run identifiers and path hashes excluded by a declared list)
    correctness does the code recover the truth it was given? a single run on simulated data with a large, known signal truth metrics against floors that sit far from both the observed distribution and the negative control
    robustness how reliably, and how well, across draws? the same case over many seeds and thread settings a distribution (median, spread, worst, failure rate against the correctness floor) recorded and compared over time; never a single-run gate
    performance how fast? benchmark reports, as today timings, never in a pass/fail test

    Consequences:

    • A correctness gate must be insensitive to the draw. Its case is built so that the right algorithm passes on every seed and thread count, by a wide margin. Its floor is set from a robustness profile of at least 20 runs: below the worst run by a stated margin, and well above what a broken algorithm or the negative control gives. If no floor satisfies both, the case is not a correctness gate; it becomes a robustness profile, or its signal is raised until it can be one.
    • Identity is the only test of a refactoring that claims identical results. It never uses multi-threaded runs. The run ms_speed settled its assignment change this way (one-thread runs byte-identical) after its multi-threaded checks had stopped it.
    • Robustness profiles inform decisions; they do not stop runs. A results-changing change, like the multi-state schedule, is judged by comparing robustness profiles before and after, on cases with known truth.

    How every high-level test is validated¶

    Each high-level test gets a test card, kept in the policy, and the card is checked by running the test, not by reading it.

    1. Claim. One sentence: the guarantee it checks.
    2. Path assertions. The test asserts, from logs or outputs, that the claimed path ran. Examples:
    3. the refine mode and number of states of each stage;
    4. that a distributed step used several worker processes;
    5. that the stage the claim concerns was reached.
    6. Truth metrics. Every gate compares with the generating truth (poses, shifts, defocus, positions, maps, state labels). Completion and consistency checks stay, but as checks, not as the gate.
    7. Calibrated floors. A robustness profile of the test (20 seeds at its CTest thread count; one thread as well where the test is deterministic) gives each metric's distribution. The card records the median, the worst run, the floor and the margin, in units of the observed spread.
    8. Sensitivity. A negative control shows the gate can fail for the right reason: run the test once with the truth deliberately broken (shuffled state labels, randomised poses, the wrong truth map) and confirm that the gate fails. A gate that passes a broken input is not a gate.
    9. Determinism class and cost. Reproducible at one thread or not; wall time and threads.

    What the inventory of 2026-10-16 already shows, test by test, is in the appendix. Every one of these becomes a card. The two broken multi-state tests are either repaired or replaced by the new multi-state tests below; that is a decision for the maintainer.

    Multi-state tests with known labels¶

    The simulator¶

    simulate_particles (simple_commanders_sim.f90, exec_simulate_particles; interface simple_ui_sim.f90) today reads one volume and sets every particle's state to 1. It learns:

    • Several volumes. nstates=K with vol1 to volK. Every particle is projected from the volume of its state. The particle loop keeps its index order, so the draws keep their order; the K padded volumes are held together, a cost stated in the documentation.
    • States from the orientation table, or drawn. A state field in oritab is respected; values outside 1 to K are refused.
    • Without one, the states are assigned from given population fractions.
    • The counts are exact: the fraction times the number of particles, rounded, with the remainder to the largest fractions. The assignment is shuffled with the seeded generator.
    • The fractions default to equal. Their key follows an existing pattern for a list of reals in the parameters, or a small text file if there is none; the run records which.
    • The truth written out. The output orientation document carries every particle's state with its pose, shift and CTF, as it does today for one state.
    • One state is unchanged. With nstates absent or 1 the program's outputs are byte-identical to today's at one thread.
    • Its documentation (doc/user_guide/simulate_particles.md and the interface text) describes the mixture.

    The fixture¶

    A test-side fixture builds a heterogeneous dataset whose labels, poses, shifts and CTF are all known, by calling simulate_particles once with all states. It has three explicit modes, because existing tests rely on contracts a pure search fixture would break:

    mode poses in the project for
    search random, with shifts no poses, no states (the truth beside it) the new multi-state tests: the programs must find poses and states
    known poses random or spiral the true poses, no states tests of state separation given the poses, as flex_pca_blobs parts 1 and 2 run today
    exact views a number of views, each repeated exactly the true poses, and the 2D class equal to the view class-average tests, as flex_pca_blobs part 3 and solve3D_pyramid_blobs run today

    The planted-state fixture of flex_pca_blobs (create_flex_pca_phantom_fixture) simulates one stack per state and interleaves them, with equal populations. The flex and pyramid tests move onto the new fixture only with the mode whose contract they need. The move keeps their contracts, not their bytes, and the moved tests are profiled again.

    • States in one frame. Every state's coordinates are edited from one model and then translated by one shared vector, so the truth maps share a frame.
    • The present pdb2mrc centres each model on its own centre, and it forces centring whenever a coordinate is negative, as 1JYX's are.
    • So the shared translation (the full model's centre to the box centre) is applied to every state before pdb2mrc runs without centring.
    • Two families.
    • Blob phantom (box 64, seconds per simulation), from the existing write_phantom_truths: a common body and a state-specific lobe. For fast logic tests.
    • Beta-galactosidase states (1JYX, embedded; waters and other het atoms dropped; box 96 at about 2.2 Å per pixel):
      • compositional states: the tetramer, the tetramer without one chain, and a dimer;
      • a conformational state: one chain rotated rigidly about the axis through its centre of mass parallel to the tetramer's long axis, by a stated angle.
    • Every truth declares its point group. The tetramer is D2, the tetramer without one chain is C1, and the dimer has the group of its two chains. The multi-state programs run in C1, so a symmetric state's particles have several equivalent true poses. A fixture check confirms each declared group: the truth map correlates with itself under every operator of its group (above 0.99), and not under the operators of the next larger group in the same family.
    • Mixture. Made by the extended simulate_particles in one call:
    • given populations, deliberately unequal (for example 50, 30 and 20%);
    • in search mode, random poses (not a spiral) and shifts within ±2-3 pixels;
    • a defocus range and a stated SNR.
    • Truth kept apart. The true state, pose and shift of every particle go into a truth document beside the project. In search mode the project the program sees carries no poses and no states. Starting volumes, where a test needs them, are the truths low-passed to a stated resolution.
    • Cached. A fixture is generated once per build from its parameters and mode, and reused by every test and every robustness run that asks for the same one.

    The metrics¶

    Shared, in simple_test_truth_metrics.f90, so every multi-state test uses the same definitions. Every metric has a unit test on synthetic inputs with a known answer.

    One state mapping for everything.

    • The estimated states are matched to the true states once: the one-to-one assignment that maximises label agreement over all permutations (up to six states).
    • That single mapping is used for:
    • the populations;
    • the maps;
    • the poses and shifts;
    • the discrimination.
    • The best map matching is also derived on its own, from the docked correlations, and the test asserts that the two mappings agree. Otherwise correct labels with swapped maps could score perfectly.

    Labels.

    • Primary: the adjusted Rand index. It is permutation-invariant, 0 in expectation for independent partitions whatever the populations, and 1 for a perfect partition.
    • Secondary: the accuracy under the mapping, judged against its own null distribution, never against 1/K:
    • The null. The true labels are shuffled across particles with the population counts kept. The matched accuracy is recomputed for each of 1,000 shuffles, giving the null's median and 99.9th percentile. With populations of 50, 30 and 20% the null sits near 0.38.
    • The collapsed predictor. Every particle in one state scores the largest population (0.50 there), and an adjusted Rand index of 0.
    • The floor. A floor on accuracy must clear both the null's 99.9th percentile and the collapsed predictor by the margin of the floor rule.
    • Unit tests.
    • A global renaming of the estimated state identifiers leaves the accuracy and the adjusted Rand index unchanged.
    • Known partitions give their published adjusted Rand values.

    Populations. The error per state, under the mapping.

    Maps, and whether they discriminate the states.

    • Docking. Each estimated map is docked (both hands) onto its mapped truth. That gives one rigid transformation per estimated state: rotation, shift and hand.
    • Fit. Per state: the band correlation and the masked FSC 0.143 with its mapped truth.
    • Discrimination, the guard against duplicated maps:
    • The difference mask is where the truths differ (the absolute difference of each truth from the others above a stated fraction of its maximum, dilated).
    • In the docked frame and inside that mask, each state's margin is its correlation with its own truth minus its highest correlation with another truth.
    • For every pair of states, the difference of the two docked estimated maps is also correlated with the difference of their truths.
    • Both must clear floors. Copies of one map have margins near 0 and a difference near 0 (or not finite, which fails).
    • The duplicated-maps negative control. Every estimated map is replaced by one of them (and once by their mean), with the truths kept distinct. The fit metrics may still pass; the discrimination metrics must fail.

    Poses and shifts.

    • Frame. Under the state's docking transformation, each particle's pose and shift are carried into the truth frame by one composition rule, with the hand's mirror applied to poses and shifts alike.
    • A unit test pins the convention: a truth rotated, shifted and mirrored by a known transformation, with poses moved accordingly, must give zero error.
    • Error. The rotation error is the smallest geodesic distance over the operators of that truth's declared point group, and only those: no group is learnt from the data.
    • So sym_pose_error, which today learns rotation clusters from the errors, is replaced, not moved: a wrong frame could become a learnt "symmetry" cluster.
    • The error is computed over the particles whose state is correct under the mapping.
    • Shifts. The error after the same transformation.

    A non-finite value fails its metric; it never maps to a pass.

    Fast¶

    • Small where signal allows. Correctness cases are sized to the smallest box and particle count at which their signal still separates them from the negative control by a wide margin. The blob tier runs in minutes, the beta-galactosidase tier in tens of minutes.
    • Fixtures cached per build instead of simulated in every test.
    • Packed by CPU reservation, not by thread count.
    • A test's thread count understates what it uses. simulated_workflow_1jxy declares one thread and launches two worker processes in its distributed step; flex_pca_blobs takes four worker threads and uses eight.
    • So every registry entry carries its peak CPU reservation: the cores in use at the busiest moment, master and workers together. That number is first derived from the test's settings and then confirmed by the profile, which samples the CPU use of each execution's process group.
    • test=nightly and test=profile pack executions so that the sum of their reservations stays within the core budget.
    • The CTest entries, kept for continuous integration, declare the reservation as their processor count instead of RUN_SERIAL, so ctest -L highlevel -j 24 packs them by the same numbers.
    • A correctness tier and a profile tier.
    • The correctness gates are what test=nightly runs, aimed at under 45 minutes on 24 cores.
    • The robustness profiles run on the weekend or on demand through test=profile.

    Execution: the run test_truth¶

    The weekend on the Oracle Linux test machine, as an unattended run in seven phases. Nothing is committed; the maintainer reviews the complete diff. Every phase records itself in the progress section.

    Common rules¶

    • Base. The HEAD the copy starts from. The run's own tests are the subject, so a test that fails on the base is a finding, not a stop.
    • Builds.
    • An out-of-tree Release build with tests (BUILD_TESTS=ON) for the profiles and the high-level runs.
    • The Debug build of ./compile_debug.sh, which runs the fast gate, for the gates.
    • Kept per phase as scratch/keep/build_phaseN.
    • Packing.
    • Profile runs are packed on the machine's 24 cores: the sum of their peak CPU reservations at most 24, with free memory watched.
    • Nothing in this run is a timing comparison, so the machine need not be idle. Wall times are recorded as the tests' cost.
    • Seeds. A profile uses seed offsets 0 to 19 (0 is the CTest draw), at the entry's CTest thread count. One-thread entries are also run twice at offset 0 and compared byte for byte.
    • Floors from profiles. Metrics where higher is better are written here; the opposite case is the mirror image. Let s be the robust spread (1.4826 times the median absolute deviation, or the observed range over 4 if that is zero). A floor is admissible when it lies:
    • at most the worst of the 20 runs minus s;
    • at most the median minus 3s;
    • at least the negative control's value plus 3s.

    If no value satisfies all three, the case is not a correctness gate. It is recorded as a robustness profile, or its signal is raised until it can be a gate. Every floor is written next to its check with its origin (the profile, its date, its median and spread). - Floors hold at one thread and on other platforms (ruling of 2026-10-18). Results at one thread reproduce on one platform but differ between compilers and machines, and refactoring runs check identity at one thread, so a gate must not fail there by chance. The floor rule's profiles cover every thread setting an entry is run at, one thread included: an entry a refactoring run checks at one thread (solve3D_addon and cont_refine3D_1jxy, the speed week's cases) is profiled at one thread as well, and its floors are set from both profiles. A floor of a case that is unchanged since the maintainer's Mac measured it is checked against the Mac's value; for a changed case the card says that the Mac has not been profiled yet. - De novo multi-state routes are a robustness measurement (ruling of 2026-10-18). De novo multi-state determination is decided by its early stages: the states start from random labels and random poses, and every assignment takes the best-scoring state outright, so whichever state fits the noise slightly better grows. Whether every true state is resolved is therefore not a per-run gate of solve3D from the particles, of the class-average route, or of single-state solve3D followed by refine3D_states: test=profile reports the number of the 20 seeds in which every true state is resolved and holds it to a floor, the observed count less three binomial standard deviations (the square root of n·p·(1−p)), rounded down, which must be above the count of the shuffled-label control. The nightly run of these routes keeps only the gates that held in every run of the profile (path assertions, pose ceilings, finite values); the label, population and state-resolution values are reported. Each seed's metrics of these routes are kept under scratch/keep/profiles/ with their seed offsets and build, the baseline of the development that will draw the state from the score differences. - Identity. A change the plan calls identical keeps the one-thread outputs of the affected tests byte-identical. test=identity checks this (until Phase 0 builds it, a byte comparison by hand), with its declared list of run-specific fields: - the run identifier in solve3D_manifest.txt; - the layout digest of sigma2_state.bin; - the manifest's stack_digest; - since Phase 0, also the manifest's layout_digest, checksum and artifact paths, with projects compared by their particle and class records (section "Tooling").

    Multi-threaded runs never decide identity. - Fix as you go (ruling of 2026-10-17, replacing "findings, not stops"). Every bug and issue found is fixed in the phase that finds it, not deferred and not only recorded: - a defect in this run's own code, or in production code that a test exposes, is fixed at once, its file added to the file table for the current phase with a one-line reason; the fix is verified by the identity check where the change is meant to be identical, otherwise by the test that found it and a profile before and after; - where the cause is a question of algorithm or design (a workflow that merges or loses states), it is diagnosed to its root cause first: a defect is fixed; a design decision is written, with the diagnosis and a proposed fix, into the progress section under "For the maintainer", and the work goes on (a stop only if the open question blocks the rest of the phase); - a floor never moves except by the floor rule.

    The run stops only when: - a change the plan calls identical cannot be made identical; - a repair needs a design the plan does not give; - a production fix would change the results of workflows beyond the defect. - Gates. - The fast gate. - The CTest unit suites of the touched areas. - python3 scripts/check_test_registry.py . whenever tests or their registration change; a new CTest entry raises SIMPLE_CTEST_BUDGET with its reason. - Release 4 rules. - No backwards compatibility. - THROW_HARD and THROW_WARN arguments are never continued with //&. - No element test of an allocatable on the line that tests its allocation. - No goto. - Dead code is deleted. - Executable bits are checked with git diff --summary. - The Windows build is not a concern.

    The simulator. simulate_particles takes nstates=K with vol1 to volK and projects every particle from the volume of its state; the K padded volumes are held together. A missing volK or a volume of another box is refused.

    • The states come from the state field of oritab when it has one (in a text orientation document, a state= key on a line; a project file always has states), and a state outside 1 to K is refused. Identity holds: the simulate_particles entry at one thread on the Phase 1 build and on this build gives byte-identical simulated_particles.mrc, simulated_oris.txt, reprojs.mrcs and reproject_oris.txt (logs/p2_simpart_p1.log, logs/p2_simpart_p2.log, compared with cmp after the last change of the phase).
